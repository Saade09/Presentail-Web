Build an advanced Login / Create Account flow matching the provided screenshots and existing app style.

Goal:
When the user taps “SIGN IN OR CREATE ACCOUNT” from the Account/Profile page, show a polished authentication modal/screen that supports:
1. Continue with email
2. Continue with Apple
3. Continue with Google

Use the same visual direction as the screenshots:
- Cream/off-white background
- Dark teal primary color
- Elegant serif headings
- Rounded modal/sheet container
- Large rounded buttons
- Thin outlined social login buttons
- Clean spacing and mobile-first layout
- Close icon on the first login screen
- Back arrow on the next step screens

Core authentication flow:

Step 1: Login or Create Account
Create a screen/modal titled:
“Login or Create Account”

Subtitle:
“Sign in with your email address”

Fields:
- Email Address
- Placeholder: “Enter your email address”

Primary button:
- “Continue”

Divider:
- horizontal line, “Or”, horizontal line

Social buttons:
- “Continue with Apple”
- “Continue with Google”

Footer text:
“By proceeding, you agree to our Privacy Policy and Terms & Conditions.”

Privacy Policy and Terms & Conditions should be tappable links using the app’s existing routes or placeholder routes if they do not exist yet.

Behavior:
- User enters email and taps Continue.
- Validate email format.
- Show inline validation if invalid.
- If valid, check whether an account exists for that email.
- If the account exists, navigate to password sign-in step.
- If the account does not exist, navigate to sign-up step.

If there is no backend/account lookup yet:
- Create a clean async function like checkEmailExists(email).
- For now, mock it clearly in one auth service file.
- Structure it so it can later be replaced with a real API call or Supabase/Firebase/Auth provider.

Step 2A: Existing account password login
If email exists, show a password sign-in screen.

Content:
- Back arrow
- Title: “Welcome back”
- Subtitle: “Enter your password to continue.”
- Show the selected email address
- Password field
- Password visibility toggle
- Primary button: “Sign in”
- Secondary link: “Forgot password?”

Behavior:
- Validate password is not empty.
- Submit login using an auth service function like signInWithEmail(email, password).
- Show loading state on button.
- Show error message if login fails.
- On success, close auth flow and update the user session/profile state.

Step 2B: New account sign-up
If email does not exist, show a sign-up screen matching the second screenshot.

Content:
- Back arrow
- Title: “Sign up”
- Subtitle: “Enter your name and create a password.”
- Name field
  - Label: “Name”
  - Placeholder: “Please add your full name”
- Password field
  - Label: “Create A Password”
  - Placeholder: “Enter your password”
  - Password visibility toggle

Password requirements section:
“Your password must contain:”
- Lower case letters (password)
- Upper case letters (PASSWORD)
- At least 8 characters including numbers

Primary button:
- “Create account”

Behavior:
- Validate name is not empty.
- Validate password live while typing.
- Show each password requirement with an incomplete/complete indicator.
- Disable “Create account” until all requirements are met.
- Submit using an auth service function like createAccountWithEmail(email, name, password).
- Show loading state.
- Show error message if account creation fails.
- On success, close auth flow and update the user session/profile state.

Social login:
Add buttons for:
- Continue with Apple
- Continue with Google

Behavior:
- Apple button should call signInWithApple().
- Google button should call signInWithGoogle().
- If auth providers are not configured yet, create placeholder service functions with clear TODO comments.
- Show loading state for the selected provider.
- Handle errors gracefully.
- Do not block the UI indefinitely.
- Keep the implementation modular so real Apple/Google auth can be added later.

UI requirements:
- Match the screenshots closely.
- First auth screen should appear as a modal/bottom sheet or full-height sheet with rounded top corners, depending on existing app patterns.
- Use a close “X” icon on the first auth screen.
- Use a back chevron on email password/sign-up steps.
- Buttons should be large, rounded, and touch-friendly.
- Inputs should have rounded borders and clear focus states.
- Use the app’s existing typography and color tokens where available.
- Maintain safe area spacing for iOS.
- Ensure the screen works correctly when the keyboard is open.
- On the sign-up screen, content should scroll if the keyboard covers the button.
- Keep the bottom action button visible or easily reachable when keyboard is open.

State management:
Create a clean auth flow state:
- email entry
- checking email
- existing user password login
- new user sign-up
- loading states
- error states

Recommended structure:
- components/auth/AuthModal or AuthSheet
- components/auth/EmailEntryStep
- components/auth/PasswordLoginStep
- components/auth/SignupStep
- components/auth/SocialAuthButtons
- services/authService
- utils/validation

Accessibility:
- Inputs should have labels.
- Buttons should have accessible names.
- Error messages should be readable by screen readers.
- Social login buttons should be clear and tappable.

Multilingual compatibility:
The app is being made multilingual.
Do not hardcode strings directly in components.
Add all auth strings to the existing i18n translation files/objects for:
- English
- Arabic
- French

Default language remains English.
Arabic must support RTL layout.
When Arabic is active:
- Back/close/chevron icons should mirror correctly where appropriate.
- Text alignment should feel natural.
- Input alignment should be correct for the selected language.
- The layout should not break.
