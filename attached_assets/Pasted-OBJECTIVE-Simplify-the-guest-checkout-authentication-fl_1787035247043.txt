OBJECTIVE

Simplify the guest checkout authentication flow so customers go directly from the cart to checkout and can optionally sign in without being forced through a preliminary popup and a separate Presentail login page.

CURRENT PROBLEM

The current journey is:
Cart → login/guest popup → standalone Presentail sign-in page → Apple/Google authentication → checkout.

This creates duplicated decisions, additional context changes, and the impression that login is required. Guest checkout is available, but it does not feel like the default low-friction path.

TARGET EXPERIENCE

The new journey should be:
Cart → Checkout.

On checkout, show a compact optional sign-in card above the existing “Recipient Details” card. The delivery form must remain visible and usable below it so customers can continue as guests without actively rejecting login.

TARGET DESKTOP COPY AND LAYOUT

Add a white rounded card in the left checkout column, between the “Delivery Details” introduction and the “Recipient Details” card.

Card copy:
- Heading: “Sign in for a faster checkout”
- Supporting text: “Use saved addresses and track your orders.”
- Button 1: “Continue with Apple”
- Button 2: “Continue with Google”
- Button 3: “Sign in with email”
- Supporting guest text: “Or continue as guest below ↓”

Visual requirements:
- Match the existing Presentail checkout design system.
- Use the existing dark teal palette, serif heading typography, sans-serif body typography, rounded controls, subtle border, and card shadow.
- Keep the card compact and visually secondary to the checkout form.
- Do not make the page look blocked, gated, or incomplete until the customer chooses an authentication option.
- Preserve the existing two-column desktop layout and sticky Order Summary behavior.

CART-TO-CHECKOUT BEHAVIOR

1. Remove the existing login/guest popup triggered by the cart checkout CTA.
2. Clicking the cart checkout CTA should take the customer directly to checkout.
3. The checkout route must support unauthenticated customers by default.
4. Do not redirect unauthenticated customers to the standalone Presentail sign-in page.
5. Preserve the cart, selected delivery method, price, promo state, card message, and any other cart configuration during navigation.

APPLE AND GOOGLE BEHAVIOR

1. Clicking Apple or Google may open the provider’s required OAuth window or redirect.
2. On successful authentication, return the customer to the same checkout session and route.
3. Prefill any available saved sender details, recipient/address information, or account data according to current product rules.
4. Never clear the cart or reset the selected delivery method.
5. If the customer has already entered checkout data, do not silently overwrite it with saved account data. Preserve entered values or ask the customer before replacing conflicting values.
6. If authentication is cancelled or fails, close the provider flow and return the customer to the same checkout state with a clear, non-blocking error message.
7. Guest checkout must remain available after cancellation or failure.

EMAIL SIGN-IN POPUP

Clicking “Sign in with email” should open a centered Presentail modal over the checkout page. Dim the page behind it with a translucent overlay, but keep the checkout context recognizable.

Initial modal content:
- Small Presentail wordmark
- Heading: “Sign in with email”
- Supporting text: “Access saved addresses and track your orders.”
- Field label: “Email Address”
- Placeholder: “Enter your email address”
- Primary CTA: “Continue”
- Helper text: “We’ll sign you in or help you create an account.”
- Divider: “OR”
- Secondary CTA: “Continue as Guest”
- Footer link: “← Back to other sign-in options”
- Close icon in the top-right

Initial popup requirements:
- Do not display a password field before the email is submitted.
- Submit on the Continue button or Enter key.
- Validate email format inline.
- Prevent duplicate submissions while loading.
- Keep the modal fully visible within the viewport.
- On mobile, use an appropriately sized full-width modal or bottom sheet with safe spacing.

After email submission:
- Existing account: continue to the current supported password, magic-link, or verification-code sign-in step inside the same modal.
- New email: do not force account creation. Clearly offer account creation and “Continue as Guest.”
- Successful sign-in: close the modal, keep the customer on checkout, preserve checkout state, and prefill eligible saved information.
- Failed sign-in: show a clear inline message without clearing the email.
- Cancel/close: close the modal and return focus to “Sign in with email.”
- “Continue as Guest”: close the modal and focus the first incomplete checkout field.
- “Back to other sign-in options”: close the email modal and return focus to the optional sign-in card.

GUEST CHECKOUT REQUIREMENTS

1. The guest delivery form must be usable immediately without clicking “Continue as Guest.”
2. The optional sign-in card must not prevent form interaction, scrolling, validation, or progression to payment.
3. A guest customer must never be redirected to authentication automatically.
4. Guest customers should proceed through the existing delivery and payment steps normally.
5. After purchase, account creation may be offered separately, but it is outside this task unless already supported.

STATE PRESERVATION

Preserve all checkout state through successful, failed, cancelled, or abandoned authentication:
- Cart items and quantities
- Product options
- Card message and sender/recipient names
- Recipient phone and address
- Delivery district and detailed address
- Delivery date/method and pricing
- Promo or gift-card state
- Sender details
- Checkout step
- Any other fields already entered

Use the existing checkout-session mechanism where possible. Ensure the OAuth return URL points back to the active checkout session rather than a generic account page.

ANALYTICS

Add or verify analytics events for:
- checkout_viewed, including authenticated/guest state
- checkout_sign_in_method_selected with method = apple, google, or email
- checkout_auth_started
- checkout_auth_completed
- checkout_auth_cancelled
- checkout_auth_failed with a safe error category
- checkout_continue_as_guest
- checkout_continue_to_payment

Include session/funnel identifiers needed to compare conversion without logging passwords, verification codes, or sensitive personal data.

Measure:
- Cart-to-checkout arrival rate
- Checkout-to-payment progression
- Checkout completion rate
- Guest versus authenticated completion
- Authentication completion/cancellation/failure
- Time from cart CTA to first checkout interaction
- Overall checkout abandonment

ACCESSIBILITY

- Modal must use the appropriate dialog semantics and accessible name.
- Move keyboard focus into the modal when it opens.
- Trap focus within the modal while open.
- Escape key and close icon must close it.
- Return focus to the triggering control after close.
- All fields and buttons require visible focus states and accessible labels.
- Error messaging must be announced to assistive technology.
- Maintain sufficient contrast and touch-target sizes.
- Do not rely on color alone to communicate state.

RESPONSIVE REQUIREMENTS

Desktop:
- Keep the sign-in card in the left column above Recipient Details.
- Do not alter the Order Summary layout or CTA.

Tablet/mobile:
- Stack sign-in options cleanly if three buttons cannot fit.
- Avoid horizontal scrolling and truncated button labels.
- Keep guest checkout visibly available.
- Ensure the email modal/bottom sheet fits above the keyboard and its CTA remains reachable.
- Test narrow devices and mobile Safari/Chrome.

ERROR AND EDGE CASES

Test and handle:
- OAuth popup blocked by browser
- Customer closes Apple/Google window
- Provider authentication failure
- Expired OAuth state or checkout session
- Existing account with incorrect password/code
- New/unrecognized email
- Slow network and repeated clicks
- Customer logs in after partially completing the guest form
- Saved account data conflicts with entered checkout data
- Customer navigates back from payment
- Multiple browser tabs
- Session/cart expiration
- Unsupported third-party cookies where relevant

QA SCENARIOS

At minimum verify:
1. Guest user goes Cart → Checkout with no popup and completes checkout.
2. Guest user ignores sign-in card and enters delivery details.
3. Apple sign-in succeeds and returns to the same checkout/cart.
4. Apple sign-in is cancelled and guest checkout remains intact.
5. Google sign-in succeeds and returns to the same checkout/cart.
6. Google sign-in fails and checkout data remains intact.
7. Email popup opens, validates invalid email, and closes correctly.
8. Existing email completes sign-in inside the modal.
9. Unknown email can continue as guest without account creation.
10. Continue as Guest closes the modal and focuses checkout.
11. Partially entered checkout data survives sign-in.
12. Desktop, tablet, and mobile layouts match the intended hierarchy.
13. Keyboard-only and screen-reader flows work.
14. Analytics fire once per intended action without duplicates.

ACCEPTANCE CRITERIA

- The cart checkout CTA takes unauthenticated customers directly to checkout.
- The old login/guest popup is removed from the cart flow.
- The standalone Presentail sign-in page is not an intermediate checkout step.
- Optional Apple, Google, and email sign-in are available on checkout.
- Guest checkout is immediately usable and requires no explicit opt-out from login.
- Email sign-in opens the specified modal and supports close, back, and guest actions.
- Authentication success returns to the active checkout session.
- Authentication failure/cancellation never empties the cart or entered checkout fields.
- Existing checkout layout, pricing, delivery selection, and Order Summary continue to work.
- Responsive and accessibility requirements pass QA.
- Analytics allow comparison of the old and new funnel.
- No regression in payment progression or order creation.

DELIVERABLES

- Updated cart-to-checkout routing
- Removed legacy pre-checkout login popup
- Checkout optional sign-in card
- Email sign-in modal and all states
- Apple/Google return handling
- Checkout-state preservation
- Analytics instrumentation
- Responsive implementation
- Accessibility implementation
- Automated tests where practical
- QA evidence for the scenarios above
- Short implementation note describing affected routes/components and any rollout or rollback considerations

ROLLOUT

Place behind a feature flag if the current checkout architecture supports it. Validate analytics in staging, run the full checkout regression suite, and monitor checkout conversion, authentication errors, and payment progression after release.
