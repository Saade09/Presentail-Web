Semrush Site Audit is reporting **32 broken internal images** across Presentail.com.

The affected image URLs are returning **HTTP 503** and appear to use our internal image proxy route:

`https://presentail.com/api/img/proxy?url=...`

The source images appear to come from Presentail OS storage, for example:

`https://os.presentail.com/api/storage/public-objects/products/318/main.png`

Affected pages span multiple markets, cities, languages, and page types, including:

* `/en-lb/aley/shop`
* `/en-lb/marjayoun/shop`
* `/fr-lb/akkar/shop`
* `/ar-lb/baabda/shop`
* `/fr-lb/hermel/shop`
* `/fr-ae/dubai/product/hallab-maamoul-mini-mixed`
* `/ar-ae/dubai/product/hallab-maamoul-mini-mixed`
* `/ar-lb/beirut/shop`
* `/ar-lb/chouf/shop`
* `/en-ae/sharjah/shop`

Semrush is specifically seeing the **image proxy return 503**.

This must be fixed as a **platform-level image delivery issue**, not by manually replacing these 32 image URLs.

# Core Requirement

Investigate why `/api/img/proxy` can return 503 for valid product images and implement a permanent, resilient image delivery architecture.

Do not:

* Hardcode fixes for the 32 URLs
* Replace each image manually
* Whitelist SemrushBot
* Serve special responses only to crawlers
* Hide broken images from Semrush
* Remove affected products
* Disable image optimization globally without understanding the cause

The goal is to make image delivery reliable for users, Googlebot, SemrushBot, social crawlers, and all other legitimate clients.

---

# 1. Reproduce the Failure

Take several affected image URLs from Semrush and request them directly.

Test:

* Normal browser request
* `curl`
* Request with Semrush-like user agent
* Request with Googlebot-like user agent
* Request with and without cache
* Multiple concurrent requests

Record:

* HTTP status
* Response headers
* Response time
* Upstream response
* Any application/server error logs

Determine whether the 503 originates from:

* Presentail application
* `/api/img/proxy`
* `os.presentail.com`
* CDN
* storage service
* timeout
* rate limiting
* concurrency limit
* DNS/network failure
* malformed URL parsing
* image transformation
* cache layer

Do not assume the source storage is broken until verified.

---

# 2. Test the Source Image Directly

For affected images, compare:

### Proxied request

`presentail.com/api/img/proxy?url=<source>`

against:

### Direct source request

`os.presentail.com/api/storage/public-objects/...`

If the direct image returns `200` while the Presentail proxy returns `503`, then the proxy is the failure point.

If both fail, investigate the storage/API layer.

Document this clearly.

---

# 3. Inspect `/api/img/proxy`

Review the implementation of our image proxy.

Check for:

* Server-side fetch timeouts
* Too-short timeout configuration
* Connection pooling issues
* Request concurrency limits
* Memory limits
* Large image buffering
* Streaming errors
* Missing error handling
* Incorrect URL encoding/decoding
* Double-encoded query parameters
* Redirect handling
* DNS failures
* Upstream TLS failures
* Unsupported response types
* Incorrect headers
* Worker/process exhaustion

The proxy should not have to load the entire image into memory before sending it if streaming is available in our architecture.

---

# 4. Investigate Why Crawling Triggers the Problem

There are **41,876 successful images and only 32 failures**, so this may be intermittent rather than a permanently invalid URL.

Investigate whether the issue appears when Semrush requests many images concurrently.

Potential causes include:

* Rate limiting
* Connection exhaustion
* Too many simultaneous upstream fetches
* Replit/runtime resource limits
* Upstream storage throttling
* Image transformation concurrency
* Cold starts
* Proxy timeout
* Cache stampede

Run controlled concurrent tests.

For example:

* 1 request
* 5 concurrent
* 10 concurrent
* 25 concurrent
* 50 concurrent

Do this safely.

Determine at what point failures begin.

---

# 5. Add Proper Caching

Our application should not repeatedly proxy the same unchanged product image from OS for every visitor/crawler.

Review whether successful proxied images have appropriate:

* `Cache-Control`
* CDN caching
* `ETag`
* `Last-Modified`
* `Age`

Product imagery should be cached aggressively where safe.

If product images are versioned or their URL changes when updated, use a long-lived immutable cache.

If URLs can point to replaced images, use an appropriate TTL/revalidation strategy instead.

The goal is:

**One upstream fetch should serve many future requests.**

---

# 6. Prevent Cache Stampedes

If 20 requests arrive simultaneously for the same uncached image, we should avoid making 20 identical upstream requests if our architecture supports request coalescing.

Consider implementing a shared in-flight request/cache mechanism where appropriate.

Do not add unnecessary complexity if our CDN already handles this correctly.

---

# 7. Improve Failure Handling

A temporary upstream issue should not unnecessarily produce broken image responses.

Implement sensible:

* Timeout handling
* Limited retry for transient failures
* Backoff
* Logging
* Error classification

Retries must be conservative.

Do not create loops or amplify an upstream outage.

For example, a retry can be appropriate for:

* `502`
* `503`
* `504`
* network timeout

but generally not for permanent errors such as `404`.

---

# 8. Do Not Return 503 for Permanent Missing Images

Ensure correct status semantics.

Examples:

### Source exists

Return `200`.

### Source permanently missing

Return appropriate `404`.

### Unsupported/bad request

Return appropriate `400`.

### Temporary upstream unavailable

A `502/503/504` may be appropriate internally, but we should minimize exposing transient failures through resilient caching/retry architecture.

Do not mask permanent 404s as successful images.

---

# 9. Image Fallback Strategy

For the user-facing frontend, implement a safe visual fallback if a product image genuinely cannot be loaded.

For example:

* Presentail product placeholder
* Neutral image placeholder

However, this is **not the main fix**.

Semrush should still be able to crawl valid product images successfully.

Do not simply return a placeholder with HTTP 200 for every upstream failure because that would hide data integrity problems.

---

# 10. Audit Image URL Generation

Ensure all image URLs generated across the site use the same reliable image service.

Search for inconsistent patterns such as:

* Direct OS storage URL
* `/api/img/proxy`
* old CDN URL
* legacy image service
* absolute vs relative paths
* different URL encoding patterns

Centralize image URL generation into a reusable helper/service where practical.

We should not have each template constructing proxy URLs independently.

---

# 11. Validate URL Encoding

The Semrush URLs appear similar to:

`/api/img/proxy?url=https://os.presentail.com/...`

Make sure nested URLs are encoded and decoded exactly once.

Test filenames containing:

* spaces
* parentheses
* Arabic characters
* French accents
* `%`
* `+`
* `&`
* query parameters

A single utility should generate these URLs consistently.

---

# 12. Review Image Optimization Architecture

Determine whether we actually need the current custom image proxy for all use cases.

If the proxy exists primarily for:

* resizing
* WebP/AVIF conversion
* CDN delivery
* CORS
* hiding storage URLs

confirm it remains the best architecture.

If our deployment/CDN/framework offers a more reliable native image optimization mechanism, evaluate whether we should migrate.

Do **not** rewrite the entire image architecture without evidence.

But if the custom proxy itself is fundamentally causing reliability problems, propose and implement the safer permanent architecture.

---

# 13. Storage Service Reliability

Inspect `os.presentail.com/api/storage/public-objects/...`.

Confirm:

* Images are publicly retrievable as intended
* Response times are acceptable
* No authentication is required
* Correct MIME type is returned
* Files are not deleted unexpectedly
* Storage is not intermittently unavailable
* Storage URLs are stable

If all 32 failures point to a specific object/product — for example product `318` — investigate whether the underlying object itself is malformed or unusually large.

From the Semrush screenshot, several failures appear to reference:

`products/318/main.png`

This is important.

Determine whether:

1. One broken/slow source image is being reused across many city/language pages, or
2. The image proxy itself is broadly unstable.

If a single shared asset creates dozens of reported failures, fix the asset/data relationship **and** ensure our system can detect this automatically in the future.

---

# 14. Add Asset Health Validation

Create a reusable validation process for product imagery.

It should be able to identify:

* Missing image files
* Broken storage references
* Source images returning non-200
* Proxy images returning non-200
* Invalid MIME types
* Zero-byte files
* Corrupted uploads where detectable
* Extremely oversized images

This should ideally operate against our product catalog rather than waiting for Semrush to discover failures.

---

# 15. Validate Images at Upload Time

When product images are uploaded into Presentail OS, validate them.

Before marking an upload successful, confirm:

* File exists
* File can be read
* Supported image format
* Non-zero file size
* Valid dimensions
* Storage returned success
* Final public URL is retrievable

If image processing/thumbnail creation is asynchronous, track processing status rather than exposing an incomplete image immediately.

---

# 16. Protect Against Broken Database References

If a product image is deleted/replaced, ensure database references are updated correctly.

Avoid situations where:

* Database points to deleted storage object
* Old image paths remain cached forever
* Product variants reference removed images
* Different locale/city pages keep obsolete URLs

Use a central asset record/reference if appropriate to our existing architecture.

---

# 17. Monitoring

Add lightweight monitoring for image proxy failures.

Track at least:

* Request count
* `2xx`
* `4xx`
* `5xx`
* Upstream timeout
* Upstream status
* Cache hit/miss
* Response duration

We should be able to detect something like:

`/api/img/proxy 503 rate > normal`

before Semrush reports dozens of broken images.

Avoid excessive/noisy logging.

---

# 18. Automated Tests

Add tests covering:

### Existing valid image

Expected: `200`

### Missing source image

Expected: correct non-200 behavior

### Encoded URL

Expected: `200`

### Arabic/Unicode filename

Expected: `200`

### Concurrent requests

Expected: stable responses

### Cached image

Expected: cached response without unnecessary upstream fetch

### Temporary upstream failure

Expected: resilient/retry behavior where appropriate

# Definition of Done

This issue is complete only when:

1. We know exactly why the image proxy returned 503.
2. The root cause is fixed at the shared image-delivery layer.
3. The existing 32 Semrush failures return correctly.
4. No URL-specific patches are used.
5. Image caching is working correctly.
6. Temporary upstream failures are handled safely.
7. Missing assets are distinguishable from temporary service errors.
8. Product image uploads/references have validation.
9. Monitoring exists for future image-proxy failures.
10. A broader crawl confirms there are no systemic image failures.

When complete, report back:

## Root Cause

Why `/api/img/proxy` was returning 503.

## Permanent Fix

What was changed in the image delivery architecture.

## Asset/Data Issues

Whether any specific source image, such as `products/318/main.png`, contributed to multiple failures.

## Before vs After

Number of broken/5xx image responses before and after.

## Caching

How image caching works after the fix.

## Guardrails

What validation, monitoring, and automated tests now prevent recurrence.

**Permanent-solution principle:** treat these 32 broken-image reports as evidence of a potential shared weakness in Presentail's image pipeline. Fix the reusable pipeline, storage/reference logic, or proxy architecture responsible rather than repairing only the URLs Semrush happened to crawl.
