#960 - Delivery cities management
What & Why
Today Presentail OS only stores a flat list of country names per workspace in Settings (available_countries). To power a future customer app delivery selector, owners need to mark which of those existing countries are active for delivery and manage a list of delivery cities under each one — without duplicating the country data.

This task extends the existing Settings > Available Countries area with:

A delivery-active toggle on each existing country.
A "Manage Cities" view per country to add/edit/activate/deactivate delivery cities.
A customer-app-safe GET /api/delivery-locations endpoint that returns delivery-active countries and their active cities.
Done looks like
In Settings > Available Countries, owners see each country they've already enabled with three new pieces of information: a "Delivery active" toggle, a count of active delivery cities, and a "Manage Cities" button.
Toggling "Delivery active" persists immediately and shows a success toast; the country card reflects the new state.
"Manage Cities" opens a view (modal or inline panel matching existing Settings patterns) listing the delivery cities for that country with: name, slug, sort order, active/inactive status, and edit/activate-deactivate/delete actions.
Owners can add a city via a form with: name (required), slug (auto-generated from name, editable, lower-kebab-case), sort order (numeric, defaults to next unused), active toggle (defaults on). Slugs must be unique within a country; duplicate slug shows an inline validation error.
Owners can edit any of those fields; toggling active and deleting a city both work. Delete asks for confirmation. Inactive cities remain in the admin list but are hidden from the customer endpoint.
A search-by-name input filters the city list. An "Active only" filter shows just active cities.
Empty states render correctly: "No delivery cities added for this country yet." when the list is empty, and "Enable delivery for this country before adding cities." when delivery is off.
Cities cannot be created against a country that isn't in the workspace's available_countries list — the backend rejects with a clear error, and the UI doesn't expose Manage Cities for non-available countries.
The UAE country, when present in available_countries, is seeded with these cities (sort order in this order, all active): Dubai (dubai), Abu Dhabi (abu-dhabi), Sharjah (sharjah), Ajman (ajman), Ras Al Khaimah (ras-al-khaimah), Fujairah (fujairah), Umm Al Quwain (umm-al-quwain), Al Ain (al-ain). Seeding is idempotent — re-running doesn't create duplicates and doesn't overwrite admin edits.
These countries are confirmed to already exist in the global WORLD_COUNTRIES list and so can be enabled for delivery whenever a workspace adds them: United Arab Emirates, Saudi Arabia, Kuwait, Oman, Qatar, Bahrain, United Kingdom, Jordan, Egypt, Lebanon. If any are missing from WORLD_COUNTRIES, they're added there (no separate countries table).
GET /api/delivery-locations returns:
{
  "countries": [
    {
      "id": "AE",
      "name": "United Arab Emirates",
      "code": "AE",
      "flag": "🇦🇪",
      "currency": "AED",
      "deliveryActive": true,
      "sortOrder": 1,
      "cities": [
        { "id": "<uuid>", "name": "Dubai", "slug": "dubai", "countryCode": "AE", "isActive": true, "sortOrder": 1 }
      ]
    }
  ]
}

Only includes countries where: the country is in available_countries, deliveryActive = true, and the country has at least one active city.
Only includes cities where isActive = true.
Countries are sorted by deliverySortOrder (ascending), then by name. Cities are sorted by sortOrder, then by name.
The endpoint is workspace-scoped using the existing workspace resolution. It is read-only and does not require admin auth (it's the customer-app surface). Authentication mode follows the existing public/customer endpoint pattern in the codebase; if no such pattern exists, the endpoint accepts the workspace identifier via the same mechanism already used by other public endpoints.
Admin endpoints follow existing settings patterns (Clerk session + resolveWorkspace, owner-only for writes, validated input, standard error responses):
GET /api/admin/settings/countries — lists this workspace's available_countries joined with delivery flags and city counts.
PATCH /api/admin/settings/countries/:countryCode/delivery — sets deliveryActive and/or deliverySortOrder.
GET /api/admin/settings/countries/:countryCode/cities — lists cities (admin-only, includes inactive).
POST /api/admin/settings/countries/:countryCode/cities — creates a city.
PATCH /api/admin/settings/cities/:id — updates name, slug, sort order, active.
DELETE /api/admin/settings/cities/:id — deletes (or soft-deletes if that's the existing convention; otherwise hard delete with confirmation).
Existing country settings, currency settings, location/checkout flows, country dropdowns, and admin forms that read available_countries continue to work unchanged.
Out of scope
Creating a new countries table or any other duplicate of the existing country source (workspace_settings.available_countries + WORLD_COUNTRIES config remains the source of truth).
Renaming or restructuring the existing Available Countries setting or available_countries column.
Building the customer-app UI that consumes /api/delivery-locations (this task only delivers the endpoint).
Delivery fees, same-day flags, cutoff times, blocked dates, vendor or product availability per city. The data model leaves obvious room for these but they are not implemented now.
Per-city geocoding, polygons, or map UI.
Localization of city names beyond the existing i18n patterns used in Settings.
Migration of existing free-text city values from locations.country or anywhere else into the new delivery_cities table.
Steps
Static country metadata lookup. Extend artifacts/print-agent-web/src/lib/countries.ts and add a matching server-side module (e.g. artifacts/api-server/src/lib/countries.ts) so each known country name maps to { name, code (ISO 3166-1 alpha-2), flag emoji, currency (ISO 4217) }. Keep WORLD_COUNTRIES (list of names) unchanged for backwards compatibility, and add an exported helper like getCountryMetadata(name). This is the single source for code/flag/currency — no new countries table is introduced. Confirm the ten countries listed in "Done looks like" are present; add any that are missing to WORLD_COUNTRIES and the metadata map.

Database schema. Add migrations in artifacts/api-server/src/lib/initDb.ts (matching the existing pattern) for two new tables, both workspace-scoped:

delivery_country_settings — (workspace_owner_id, country_code) composite primary key, plus delivery_active boolean NOT NULL DEFAULT false, delivery_sort_order integer NOT NULL DEFAULT 0, created_at, updated_at. Stores delivery metadata for an available_countries entry without duplicating the country list.
delivery_cities — id (uuid or serial, matching existing convention), workspace_owner_id, country_code (text, links logically to delivery_country_settings.country_code), name, slug, sort_order integer NOT NULL DEFAULT 0, is_active boolean NOT NULL DEFAULT true, created_at, updated_at. Indexes: (workspace_owner_id, country_code), (workspace_owner_id, is_active), and a unique index on (workspace_owner_id, country_code, slug). Match the soft-delete vs hard-delete convention used by base_item_categories (which is the closest parent/child sibling in Settings).
Admin API endpoints. In artifacts/api-server/src/routes/, add a new router (e.g. settings-delivery.ts) mounted under the existing settings router, using requireAuth + resolveWorkspace and an owner-only check for writes (mirror routes/settings.ts). Implement the six endpoints under /api/admin/settings/... listed in "Done looks like". Validate that any :countryCode is present in the workspace's available_countries (translate name ↔ code via the metadata helper) before allowing delivery toggle or city creation; reject with 400 + a clear error code when not. Auto-generate slug server-side if not provided and enforce per-country slug uniqueness. Strip excluded countries (isExcludedCountry) defensively. Keep the existing settings endpoint behavior unchanged.

Customer endpoint. Add GET /api/delivery-locations returning the response shape described above. Workspace scoping: follow whatever pattern existing customer-facing endpoints use (e.g. workspace identifier via header/query); if none exists, expose it under the same workspace resolution as the admin endpoints for now and note that the customer app integration will refine this. The handler joins available_countries ∩ delivery_country_settings.delivery_active = true ∩ has-active-cities, decorates with metadata (code, flag, currency), embeds active cities sorted by sort_order then name, and excludes anything caught by isExcludedCountry.

OpenAPI spec & codegen. Add a Delivery (or Settings.Delivery) tag and full schemas + paths for the six admin endpoints and the public endpoint to lib/api-spec/openapi.yaml. Run pnpm --filter @workspace/api-spec run codegen so Zod schemas and React Query hooks are generated for the admin UI to consume.

Settings UI: country row extensions. In artifacts/print-agent-web/src/pages/dashboard/Settings.tsx, extend the Available Countries card so each currently-selected country renders a row (instead of just a checkbox label) with: flag, country name, code, currency, the existing select-for-workspace checkbox (preserved), a "Delivery active" toggle, an active-cities count, and a "Manage Cities" button. The country selection list itself (the searchable checklist of all WORLD_COUNTRIES) keeps its current behaviour — delivery controls only appear for countries already in available_countries.

Settings UI: Manage Cities view. Build a Manage Cities view (modal or expandable section, matching BaseItemCategoriesCard patterns for parent/child management) showing the country header (flag + name) and the city table with name, slug, sort order, active toggle, edit, and delete. Include an "Add City" form with the validation rules above (auto-generated slug from name with manual override, inline duplicate-slug error, success/error toasts), search-by-name, an active-only filter, a delete confirmation, and the two empty states. Use existing Card, Input, Checkbox, Button, Dialog/modal, and useToast components. Add data-testid attributes mirroring nearby Settings code (e.g. delivery-active-toggle-<code>, manage-cities-button-<code>, add-city-button, city-row-<id>).

UAE seed data. Add an idempotent server-side seed step (run from the existing init/migration flow in initDb.ts, the same place base_item_categories and other defaults are seeded) that, for any workspace whose available_countries includes "United Arab Emirates", inserts the eight UAE cities listed in "Done looks like" if they don't already exist by (workspace_owner_id, country_code='AE', slug). Do not overwrite admin-edited rows. Do not seed delivery-active state — admins flip that themselves.

i18n strings. Add the new user-visible strings (column headers, button labels, empty states, validation messages, toasts) to the existing translation files used by Settings.tsx. Match the style/keys of nearby settings.* strings (e.g. settings.deliveryActive, settings.manageCities, settings.cityNameRequired, settings.slugDuplicate).

Tests. Add server tests (matching the style of routes/settings.test.ts) covering: GET admin countries returns the joined shape; PATCH delivery toggle persists and round-trips; POST city validates required fields, slug uniqueness, and rejects unknown countries; PATCH and DELETE city; the public /api/delivery-locations filtering and sort rules; UAE seed runs idempotently. Add at least one e2e test (Playwright, matching the patterns in available-countries-db-e2e/base-items-filters-e2e) that toggles delivery on UAE, opens Manage Cities, adds a city, deactivates it, and verifies the customer endpoint reflects the changes.
