Add push notification permission support to the app. This feature does not currently exist.

Goal:
Implement a first-time notification permission flow so the app can ask users if they want to receive notifications.

Recommended behavior:
Do not show the native OS notification permission popup immediately on app launch without context.

Instead, show a branded in-app permission screen or modal first, then trigger the native permission prompt only if the user taps “Allow Notifications.”

Where to ask:
Show the notification prompt after one of these moments:
1. After the user signs in or creates an account for the first time.
2. After the user places their first order.
3. If neither flow exists yet, show it after the user opens the app for the first time and reaches the Home screen, but only after a short delay so it does not feel abrupt.

Create the structure so the trigger can be moved later.

In-app permission prompt copy:
Title:
“Stay updated on your gifts”

Subtitle:
“Get notified about order updates, delivery progress, special moments, and reminders so you never miss an important gift.”

Primary button:
“Allow Notifications”

Secondary button:
“Maybe Later”

Behavior:
- If user taps “Allow Notifications,” request native push notification permission.
- If user grants permission, save notification permission status locally.
- If user denies permission, save denied status locally.
- If user taps “Maybe Later,” dismiss the prompt and save that it was skipped.
- Do not show the prompt repeatedly every time the app opens.
- Allow the app to ask again later from Settings/Profile if the user previously tapped “Maybe Later.”
- If the user denied native permissions, direct them to system settings if they try to enable notifications again.

Platform support:
iOS:
- Request notification permission using the appropriate native API/library already used by the project.
- Support alert, sound, and badge permissions.
- Handle granted, denied, provisional, and not determined states if available.

Android:
- For Android 13/API 33+, request POST_NOTIFICATIONS runtime permission.
- For older Android versions, handle notifications as allowed unless disabled by system/app settings.
- Handle denied and granted states correctly.

If the app is Expo:
- Use expo-notifications.
- Configure notification permissions properly.
- Add any required app.json/app.config changes.
- Add iOS notification usage strings if needed.
- Add Android notification permission configuration if needed.

If the app is React Native bare:
- Use the existing notification library if present.
- Otherwise add a clean notification permission service abstraction and document what library/config is needed.

Important:
- Do not implement real push campaigns or backend notification sending yet.
- This task is only for permission handling and local app state.
- Keep the notification logic modular so backend push token registration can be added later.

Files/structure to create or update:
- services/notifications or utils/notifications
- notification permission helper/service
- reusable NotificationPermissionModal component
- app startup or auth success hook where the prompt is triggered
- local storage key for notification prompt state
- i18n translation files/objects
- Profile/Settings entry point for enabling notifications later, if a settings area already exists

Suggested notification state values:
- not_determined
- prompted
- granted
- denied
- skipped

Persistence:
Save locally:
- Whether the in-app prompt was shown
- Whether the user skipped it
- Native permission status
- Timestamp of the prompt if useful
