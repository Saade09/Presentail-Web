Required flow

Change the current flow from:

Microform tokenization
→ Payments API authorization/capture

to:

Microform tokenization
→ Payer Authentication setup
→ Device data collection
→ Check enrollment/authentication
→ Frictionless result or issuer challenge
→ Validate challenge result when required
→ Payments API authorization/capture with 3DS data

CyberSource documents separate REST endpoints for authentication and authentication-result validation.

1. Tokenize with the existing Microform

Keep the current working Microform implementation.

After card details are valid, create the transient token:

microform.createToken(...)

Never expose or log:

PAN
CVC
complete transient token

Store the transient token only for the duration of the payment attempt.

2. Payer Authentication setup

Add a backend endpoint:

POST /api/payments/cybersource/payer-auth/setup

It must call:

Production:
POST https://api.cybersource.com/risk/v1/authentication-setups

Test:
POST https://apitest.cybersource.com/risk/v1/authentication-setups

Send the Microform transient token using the exact field structure required by the current CyberSource API version.

The setup response should provide safe client-side data required for device collection, including:

access token
device data collection URL
reference ID

CyberSource requires setup before device-data collection in the Direct API integration.

Return only the minimum required values to the frontend.

3. Device data collection

Add an invisible device-data iframe using the URL and access token returned by CyberSource.

Requirements:

Use the exact URL returned by the setup response.
Submit the access token according to CyberSource’s documented method.
Wait for completion or a controlled timeout.
Continue using the returned referenceId.
Do not show a broken or oversized iframe.
Do not block the checkout permanently if collection times out.

Add a temporary payment state:

collecting_device_data
4. Check enrollment and request authentication

Add a backend endpoint:

POST /api/payments/cybersource/payer-auth/check-enrollment

It must call:

POST https://api.cybersource.com/risk/v1/authentications

The request must include the applicable CyberSource fields for:

transient token
device-data reference ID
amount
USD currency
bill-to information
customer email and phone
return URL
browser information
client reference/order reference
merchant-defined data where currently used

Supply complete browser data from the checkout:

{
  acceptHeader,
  userAgent,
  language,
  colorDepth,
  screenHeight,
  screenWidth,
  timeZone,
  javaEnabled,
  javaScriptEnabled,
  ipAddress
}

Use CyberSource’s exact current field names rather than inventing mappings.

5. Handle frictionless authentication

When authentication succeeds without a challenge:

Confirm the returned authentication status is acceptable.
Extract the required 3DS authorization values.
Continue to the payment authorization.

Preserve relevant safe metadata:

{
  authenticationTransactionId,
  directoryServerTransactionId,
  specificationVersion,
  ecommerceIndicator,
  cavv,
  xid,
  paresStatus,
  veresEnrolled
}

Store sensitive authentication values server-side only where possible.

Do not assume that “no challenge” means authentication succeeded. Evaluate the exact response status.

6. Handle issuer challenge

When the check-enrollment response requires a challenge:

Display the returned issuer/CyberSource step-up experience in a secure modal or iframe.
Use the returned step-up URL and access token/JWT exactly as documented.
Do not build or imitate the bank challenge UI.
Prevent checkout resubmission while the challenge is active.
Do not authorize payment before challenge validation.

Add state:

authentication_pending

Support:

challenge success
challenge failure
customer cancellation
timeout
iframe load failure
browser back navigation
page refresh
7. Validate the authentication result

Add:

POST /api/payments/cybersource/payer-auth/validate

It must call:

POST https://api.cybersource.com/risk/v1/authentication-results

This endpoint validates the challenge result before payment authorization.

Continue to payment only when the validated result meets the CyberSource/BLOM-approved success policy.

Failed, rejected or abandoned authentication must not charge the card.

8. Include authentication data in authorization

Modify only the CyberSource payment request so that /pts/v2/payments receives the Payer Authentication values returned by the successful authentication result.

Use CyberSource’s documented mapping for:

commerce indicator
CAVV/AAV
ECI
XID when applicable
3DS version
directory server transaction ID
authentication transaction ID

Do not authorize the same authentication result more than once. Authentication data is tied to the authorization attempt. CyberSource requires the appropriate authentication data to be passed into authorization.

Continue using:

{
  "processingInformation": {
    "capture": true
  }
}

only if the current production flow is intentionally sale/immediate capture.

9. Order and retry protection

Add an idempotent payment-attempt ID.

The same checkout must not:

create two CyberSource payments
create two orders
reuse successful authentication data
authorize again after browser refresh
submit while a challenge is pending

Suggested states:

card_tokenized
collecting_device_data
authentication_pending
authentication_succeeded
authentication_failed
authorization_pending
payment_approved
payment_failed

Mark the order paid only after CyberSource returns an approved payment result.

10. Error messages

Replace generic errors with stage-specific messages:

Setup failure → Card verification could not be started
Device collection timeout → Card verification timed out
Authentication challenge cancelled → Card verification was cancelled
Authentication failed → Your bank could not verify this payment
Processor decline → Card declined
Payment API unavailable → Card payment is temporarily unavailable

Do not call an authentication failure a payment decline.

Acceptance criteria
Lebanon sender + USD invokes Payer Authentication.
Other country/currency combinations remain unchanged.
Setup calls /risk/v1/authentication-setups.
Device-data collection completes.
Enrollment/authentication calls /risk/v1/authentications.
Frictionless success proceeds to authorization with 3DS values.
Challenge-required test displays the issuer challenge.
Successful challenge calls /risk/v1/authentication-results.
Failed or cancelled authentication does not charge the card.
CyberSource payment records show Payer Authentication/3DS information.
No duplicate charge or duplicate order is possible.
Disabling the feature flag restores the current working flow.
