Here's exactly how product availability by country and city is stored and how the website should read it.

The tables
There are two override tables (both use a "default-on" model — a product is available everywhere unless a row explicitly turns it off):

product_country_availability

column	meaning
product_id	which product
country_code	ISO code, uppercase — CY, LB, AE
is_available	false = hide product in this country
product_city_availability

column	meaning
product_id	which product
city_id	references delivery_cities.id
is_available	false = hide product in this city
The countries/cities themselves live in delivery_cities (id, country_code, name, slug, is_active, …). That's the master list the checkboxes in your screenshot are built from.

So when an owner unchecks "Lebanon" or "Beirut", a row gets written with is_available = false. Everything left checked has no row (it's available by default).

How the website reads it
The public storefront does not read those tables directly — it passes the visitor's location to the catalog API and the server does the filtering:

GET /api/public/catalog/products?workspace=<slug-or-id>&country_code=LB
GET /api/public/catalog/products?workspace=<slug-or-id>&city_slug=beirut
GET /api/public/catalog/products?workspace=<slug-or-id>&city_id=42

The server then hides any product that has an explicit is_available = false row for that city or country, and returns only what's still available:

{ "products": [ … ], "total": 100, "page": 1, "pageSize": 25, "totalPages": 4 }

To get the list of countries/cities to show as options, the site calls:

GET /api/delivery-locations?workspace=<id>

Why your screenshot "still shows" everything
The filtering only kicks in when the request includes a city/country. If the website calls /api/public/catalog/products without country_code, city_slug, or city_id, the server has nothing to filter on and returns every available product — so unchecking cities has no visible effect.

So the most likely fix is on the website side: it needs to send the visitor's resolved city_slug (or country_code) on the catalog request.
