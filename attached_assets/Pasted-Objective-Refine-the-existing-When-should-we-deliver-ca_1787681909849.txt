Objective
Refine the existing “When should we deliver?” cart popup so customers can compare and confirm delivery options quickly, without the header, close action, time options, or confirmation CTA being pushed outside the viewport.

Background / current issue
The existing popup becomes taller than the usable browser viewport. On smaller laptop screens and short viewport heights, users must scroll inside the modal: the title and close button can disappear at one scroll position, while the confirmation button can disappear at another. The UI also spends significant space displaying time windows that have already passed and cannot be selected.

Approved design direction
Use the two attached approved mockups as the visual source of truth:
1. Some earlier windows unavailable: keep every available option visible and collapse only unavailable/past windows.
2. All windows available: show all five available time windows in a compact layout.

Required UI changes
1. Modal shell and hierarchy
- Keep the title “When should we deliver?”, supporting copy, and close button visible.
- Use a shorter, compact modal with efficient vertical spacing.
- Maintain the existing Presentail visual language: cream/white surface, dark teal selection states, rounded borders, serif heading, and accessible contrast.
- Avoid oversized cards or large unused gaps.

2. Delivery option control
- Convert Express and Schedule from tall cards into a compact two-option segmented control.
- Express should communicate the customer-facing arrival promise when available, e.g. “Arrives by 9:00 PM”, plus its surcharge.
- Schedule remains selected when the customer is selecting a date/time and displays “Pick a date & time”.
- Preserve existing business logic, pricing, eligibility, and selection persistence.

3. Date selection
- Show Today, Tomorrow, the next displayed date, and Another date as compact chips.
- Preserve the current calendar/custom-date behavior.
- Selected date must have a clear dark teal state.
- Date and slot availability must refresh correctly when the customer changes date, district, city, cart contents, or delivery option.

4. Dynamic time-slot behavior
A. When some earlier slots are unavailable:
- Never hide an available slot.
- Collapse only unavailable/past slots into one compact expandable disclosure row.
- Example: “3 earlier windows are unavailable today” with a chevron.
- Expanding the row reveals the disabled slots for transparency; collapsing returns to the compact state.
- Disabled slots remain non-interactive and visually distinct.
- Default state is collapsed.

B. When all slots are available:
- Show all five windows; do not display the unavailable disclosure.
- Use two compact rows for the first four slots:
  • 9 AM–2 PM — Morning
  • 2 PM–6 PM — Afternoon
  • 6 PM–10 PM — Evening
  • 9 PM–11 PM — Late night
- Display Midnight Delivery as a compact full-width fifth row:
  • 11 PM–1 AM
  • “Ends the next day”
  • Applicable surcharge
- Do not leave an empty grid cell.

C. When no slots are available for the selected date:
- Clearly state that the selected date is fully booked/unavailable.
- Offer or automatically highlight the next date with availability, without silently changing the confirmed selection.
- The user must explicitly confirm the new date/time.

5. Time and midnight copy
- For a same-day 9 PM–11 PM selection, use “Tonight” where appropriate.
- For the midnight window, clearly communicate the date boundary: “11 PM–1 AM” and “Ends the next day”.
- Use the existing locale/currency formatting and preserve the configured surcharge.
- Price pills should be visible but subordinate to the time-window label.

6. Selection and footer
- Selected time has a dark teal border and check indicator.
- The confirmation footer remains visible while the modal content changes.
- “Cancel” is a secondary text action.
- The primary CTA dynamically reflects the selection, e.g.:
  • “Confirm tonight, 9 PM–11 PM · +20”
  • “Confirm delivery” / “9 AM–2 PM”
- Disable confirmation until a valid date and slot are selected.
- Confirming updates the cart delivery summary and closes the popup.

Responsive requirements — critical
The popup must be fully responsive. No title, close button, available slot, surcharge, Cancel action, or confirmation CTA may be clipped or rendered outside the usable viewport.

Desktop and smaller laptops:
- Modal width should be responsive, approximately min(680px, calc(100vw - 32px)).
- Modal max height should respect the dynamic viewport, approximately calc(100dvh - 32px).
- At common short laptop viewports (including 1280×720 and 1366×768), the compact all-slots-available state should fit without scrolling whenever practical.
- Header and footer must remain visible if internal scrolling becomes necessary at exceptional zoom or viewport heights.

Tablet and mobile web:
- Adapt to a full-height modal or bottom sheet based on the existing design system.
- Use 100dvh and safe-area insets; do not rely only on 100vh.
- Prevent the underlying cart page from scrolling while the popup is open.
- On narrow widths, stack controls cleanly and use compact single-column time rows if two columns would reduce legibility.
- Preserve minimum 44×44px tap targets.
- If content cannot physically fit at once, only the middle content area may scroll; header/close and confirmation footer must stay sticky and continuously accessible.
- No horizontal scrolling.
- Test at minimum: 320×568, 375×667, 390×844, 430×932, 768×1024, 1280×720, and 1366×768.
- Verify 100%, 125%, and 150% browser zoom, long localized strings, and device safe areas.

Accessibility and interaction
- Implement as an accessible modal/dialog with focus trapping, Escape-to-close on desktop, and focus returned to the trigger on close.
- All segmented controls, date chips, disclosure control, and time slots must be keyboard accessible.
- Use semantic radio/selection behavior and announce disabled/unavailable states.
- Maintain visible focus styling and sufficient color contrast.

Acceptance criteria
- Both attached approved states are implemented responsively.
- Available time windows are never hidden.
- Past/unavailable windows are collapsed by default only when present and can be expanded.
- All five available windows fit in the compact desktop layout with no empty grid cell.
- Header, close action, and confirmation footer remain accessible at every supported viewport.
- No clipping, overlap, horizontal scroll, or page-background scroll.
- CTA copy, selected date/time, surcharge, cart summary, and persisted delivery data remain synchronized.
- Existing Express/Schedule, date availability, district/city, pricing, and checkout logic continue to work.
- QA covers all availability states, viewport sizes, zoom levels, keyboard behavior, and both LTR/RTL layouts if this shared component supports Arabic.
