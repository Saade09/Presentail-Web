Amend Task #4167 before implementation.

The overall Unified Checkout architecture is approved, but the following corrections are mandatory.

## 1. Do not use TSS as the primary real-time payment gate

`GET /tss/v2/transactions/{requestId}` must not be the primary synchronous verification step before order creation.

CyberSource documents the Transaction Details API as a reporting API that is not intended for real-time transaction processing and can respond slowly.

Use it only for:

* reconciliation
* delayed fallback checks
* historical transaction investigation
* recovery of stuck attempts

The durable server-side completion source must be the CyberSource Unified Checkout webhook:

* product ID: `unifiedCheckout`
* event type: `uc.orders.transactionresults`

Configure the required webhook subscription, digital-signature validation, and message-level encryption/decryption.

The webhook handler must:

1. Validate the webhook signature.
2. Decrypt the MLE payload.
3. Match the payload to the stored payment attempt.
4. Verify merchant ID.
5. Verify the unique client reference.
6. Verify the exact amount.
7. Verify the currency is USD.
8. Verify the CyberSource request ID.
9. Verify the final payment status and outcome.
10. Create exactly one Presentail order.
11. Queue or perform OS synchronization idempotently.
12. Mark the payment attempt completed.
13. Safely accept duplicate webhook deliveries without creating another order.

The browser-returned result must never be sufficient by itself to mark an order paid.

The browser result can move the attempt into `AWAITING_SERVER_CONFIRMATION`, while the webhook provides durable confirmation.

## 2. Confirm the actual Unified Checkout SDK version

Do not assume `onResult` is the correct completion API.

Log and document:

* exact CyberSource JavaScript URL
* exact client library version from the capture context
* Subresource Integrity value
* whether the implementation uses Unified Checkout v0 or v1
* the documented initialization and completion method for that version

For Unified Checkout v1 with automatic processing, use the documented structure:

```javascript
const client = await window.VAS.UnifiedCheckout(sessionJwt);
const checkout = await client.createCheckout({
  autoProcessing: true,
});

const paymentResult = await checkout.mount(target);
```

Treat the resolved `mount()` result as the browser-side completion result unless the exact loaded SDK documentation specifies a different method.

Do not implement an unsupported or assumed `onResult` callback.

## 3. Verify the capture-context configuration

Log the complete non-sensitive capture-context request and verify it contains the intended production configuration, including:

```json
{
  "completeMandate": {
    "type": "CAPTURE",
    "consumerAuthentication": "3DS"
  }
}
```

Also verify:

* production target origin
* production merchant ID
* USD amount
* allowed card networks
* `PANENTRY` in allowed payment types
* correct client version
* correct return and webhook correlation references

Do not manually call legacy Setup, Check Enrollment, Validate Authentication, or REST authorization when this Unified Checkout attempt is active.

## 4. Activate both flags correctly

Confirm the effective production values of:

```text
CYBERSOURCE_UNIFIED_CHECKOUT_ENABLED
VITE_CYBERSOURCE_UNIFIED_CHECKOUT_ENABLED
```

Because the `VITE_` value is compiled into the browser bundle, rebuild and redeploy the frontend after enabling it.

Add startup and browser diagnostics that state:

```text
CyberSource server UC enabled: true/false
CyberSource client UC enabled: true/false
Selected LB+USD path: unified-checkout/microform
```

Do not expose secret values.

## 5. Use explicit payment states

Track these separately:

```text
authentication_status
authorization_status
capture_status
order_status
os_sync_status
```

Setup, enrollment, challenge completion, or authentication success must never be treated as payment success.

Only approved Unified Checkout payment results may proceed to order creation.

The final accepted states must be explicitly mapped from CyberSource responses. Unknown, pending, or incomplete statuses must remain pending and must not create an order.

## 6. Legacy-path rejection

Keep the proposed HTTP 409 protection.

Any attempt created as Unified Checkout must be rejected by:

* Microform tokenization endpoints
* legacy Setup endpoint
* legacy Check Enrollment endpoint
* legacy Validate Authentication endpoint
* legacy REST authorization path

Any legacy attempt must also be rejected by Unified Checkout completion endpoints.

One attempt may use exactly one payment integration path.

## 7. Required testing evidence

Before deployment, provide logs proving:

1. The LB+USD checkout renders `CyberSourceUnifiedCheckout`.
2. The browser initializes `window.VAS.UnifiedCheckout`.
3. The capture context contains `consumerAuthentication: "3DS"`.
4. No legacy payer-auth endpoint is called.
5. A challenged test payment returns a Unified Checkout payment request ID.
6. The Unified Checkout webhook is received and validated.
7. The webhook reports the final payment result.
8. Exactly one website order is created.
9. Exactly one OS synchronization is created.
10. The original browser tab redirects to confirmation.
11. CyberSource/BLOM displays the transaction under Unified Checkout rather than the Microform REST path.
12. TSS is used only for reconciliation or delayed fallback, not primary checkout completion.
