Fix the CyberSource 3DS completion flow so an approved authentication always results in exactly one recorded Presentail order and the original checkout tab redirects to the confirmation page.

The current proposal is incomplete because the observed authentication flow opens in a separate browser tab. Do not assume this is only an iframe escaping into the top frame.

## Required architecture

Create a persistent server-side CyberSource payment-attempt record before starting payer authentication. React state and sessionStorage must not be the authoritative source.

Store:

* internal attemptId
* checkout/cart ID
* customer or guest-session ID
* amount
* currency
* CyberSource authenticationTransactionId
* CyberSource request/authorization ID
* current payment status
* order ID
* OS order ID
* error details
* created and updated timestamps

Do not store CyberSource transient payment tokens in localStorage or sessionStorage. Send them immediately to the backend and process them server-side.

## Challenge return handling

Support all three return contexts:

1. Separate authentication tab:

   * Detect `window.opener`.
   * Send a `CYBERSOURCE_3DS_COMPLETE` message to the original checkout tab using `window.opener.postMessage`.
   * Use the exact allowed checkout origin, never `*`.
   * Include only the opaque internal attemptId and returned authenticationTransactionId.
   * Close the authentication tab after the original tab acknowledges receipt.

2. Challenge iframe:

   * Use `window.parent.postMessage` with the exact allowed origin.
   * Close the challenge modal after acknowledgement.

3. Top-level fallback:

   * Redirect to `/checkout/payment-resume?attempt=<attemptId>`.
   * The resume page must retrieve the attempt status from the backend.
   * Never trust transaction data from URL parameters without server verification.

Remove `allow-top-navigation-by-user-activation` from the challenge iframe unless CyberSource documentation proves that it is required. Preserve the permissions required for the issuer challenge to function.

## Backend-controlled completion

After CyberSource posts to the payer-auth return endpoint:

1. Parse and validate the returned TransactionId and merchant data.
2. Match them to the existing server-side payment attempt.
3. Call CyberSource Validate Authentication.
4. Verify the final authentication result and required 3DS fields.
5. Perform or confirm authorization using the validated authentication values.
6. Store the CyberSource request ID and authorization result.
7. Create the Presentail website and OS order server-side.
8. Mark the attempt `COMPLETED`.
9. Return the existing order if completion is called again.

Do not depend on the original browser tab to perform the authorization or create the order.

## Idempotency

Enforce exactly one order per payment attempt and CyberSource authorization.

Add database uniqueness protections for:

* attemptId
* CyberSource request/authorization ID
* payment-attempt-to-order relationship

Every resume, callback, polling, retry, and message event must be safe to execute multiple times.

Never submit a second authorization when an approved authorization already exists.

## Original checkout behavior

The original checkout tab must:

* listen for `CYBERSOURCE_3DS_COMPLETE`
* verify `event.origin`
* verify that the attemptId matches the active checkout
* call a backend status/resume endpoint
* show “Finalizing your order” while waiting
* poll the backend if the popup message is missed
* redirect to `/order-confirmation/<orderId>` only when the backend reports `COMPLETED`
* show a recoverable error when authorization succeeded but order creation is still retrying

The frontend must also recover after refresh by reading the opaque attemptId and requesting its current backend status.

## Recovery and reconciliation

Add a reconciliation path for CyberSource transactions that are authorized but have no Presentail order.

For the currently affected transaction:

* retrieve its CyberSource status using the request ID or merchant reference
* verify whether it is authorized, captured, reversed, pending, or failed
* search the website and OS databases for an existing order using the attempt ID, merchant reference, and CyberSource request ID
* if approved and no order exists, create the order idempotently from the stored checkout snapshot
* if the order cannot validly be created, flag the authorization for void/reversal
* never recharge the customer

Add structured logs covering:

* attempt creation
* check enrollment
* challenge opened
* challenge return received
* validation response
* authorization response
* order creation
* OS synchronization
* confirmation redirect
* reconciliation action

## Acceptance criteria

* Successful frictionless 3DS creates exactly one order and redirects to confirmation.
* Successful iframe challenge creates exactly one order and redirects the original checkout tab.
* Successful separate-tab challenge closes the authentication tab and redirects the original checkout tab.
* Refreshing either tab does not lose the payment attempt.
* A missed postMessage is recovered through backend polling.
* Repeated callbacks and resume requests never create duplicate orders or duplicate charges.
* An approved CyberSource authorization followed by a temporary OS failure is retried safely until the order is recorded.
* Failed or rejected authentication does not authorize the payment.
* Existing authorized transactions without orders can be reconciled without charging again.
* Stripe and all non-CyberSource payment flows remain unchanged.
