Completely remove the existing CyberSource integration from the entire Presentail application. The objective is to return the codebase to a clean pre-CyberSource state so a new Unified Checkout integration with Payer Authentication can later be built from scratch.

Do not reinstall or rebuild CyberSource during this task.

## Mandatory preservation rule

Do not delete or alter:

* Completed orders
* Captured payment amounts
* Refund records
* Existing CyberSource transaction IDs
* Accounting or reconciliation records
* Historical payment-provider values needed to display old orders

Historical CyberSource data must become read-only legacy data. It must never trigger API calls or active CyberSource behavior.

## 1. Inventory the existing integration

Search the entire repository, including frontend, backend, mobile app, tests, configuration, migrations, documentation, scheduled jobs and deployment files.

Search case-insensitively for at least:

* `cybersource`
* `CyberSource`
* `CYBERSOURCE`

* `Flex`

* CyberSource merchant IDs, API hosts and SDK URLs
* CyberSource webhook paths
* CyberSource-specific payment-provider enum values
* CyberSource feature flags and eligibility helpers

Before editing, produce an internal inventory of every affected file and dependency. Then perform the removal.

* CyberSource eligibility logic based on IP, currency or delivery country

Remove dead imports, exports, hooks, state variables, feature flags and conditional branches left behind.

Do not leave commented-out CyberSource code.

## 7. Clean payment routing

Remove CyberSource from payment-provider selection and checkout routing.

Requirements:

* No customer may be routed to CyberSource.
* No CyberSource component, request or SDK may load.
* Existing non-CyberSource payment methods must remain unchanged.
* Do not silently reroute Lebanon + USD payments to Stripe unless that route was already independently supported and valid.
* If Lebanon + USD has no valid card processor after removal, show a controlled “card payment is temporarily unavailable” state instead of attempting CyberSource or creating an invalid payment.
* Cash or other independently supported payment methods must continue working.
* Order creation must not expect a CyberSource request ID, token, authorization result or webhook.

## 8. Handle database artifacts safely

Inspect all CyberSource-specific database columns, tables, enums and indexes.

Do not modify or delete historical financial data.

Apply these rules:

* Remove tables or columns only when they contain no historical transaction or reconciliation data.
* Do not edit old migration files that may already have run in production.
* Use a new forward migration for safe schema cleanup.
* Preserve old provider and transaction identifiers required to display historical orders.
* Convert active CyberSource processing fields into read-only legacy metadata where required.
* No new order may write CyberSource-specific data.
* No historical CyberSource record may cause a webhook, refund, reconciliation or API call.
* The application must still open and display historical orders whose provider was CyberSource.
