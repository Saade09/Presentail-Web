OBJECTIVE

Implement the approved visual-polish pass for the Delivery Details checkout page so the form has clearer hierarchy, stronger progress visibility, more intentional proportions, better grouping, and a consistent premium Presentail typography system.

This task is visual and responsive implementation work. It should preserve all existing checkout behavior and integrate cleanly with the related recipient-name/phone-tooltip task.

RELATED TASK

Checkout: merge recipient name fields and add phone-number info tooltip
Checkout: merge recipient name fields and add phone-number info tooltip

The final UI must accommodate the single “Recipient name” field and the phone-number information icon defined in that task.

APPROVED DESIGN DIRECTION

The approved state uses:
- A shorter, more efficient checkout header.
- A larger, higher-contrast two-step progress indicator.
- A pale-teal address-collection choice card.
- A more balanced form/summary grid.
- Consistent capped input widths.
- Stronger grouping through spacing.
- Serif typography for meaningful page and card headings.
- Two clearly separate left-column cards.
- No horizontal decorative rules beside card headings.
- A closed-by-default phone tooltip icon.
- Existing order-summary content and checkout CTA preserved.

SCOPE

1. CHECKOUT HEADER

- Reduce the dark teal checkout header height by approximately 20–25% from the current production implementation.
- Keep sufficient vertical padding for the Presentail logo, progress indicator, and Back to Cart action.
- Preserve the existing dark Presentail teal background.
- Keep the Presentail logo left-aligned within the page container.
- Keep Back to Cart right-aligned and vertically centered.
- Ensure all header elements share one intentional vertical centerline.
- Do not reduce mobile touch targets while reducing the visual height.

2. PROGRESS INDICATOR

- Keep the two steps:
  1. Delivery Details
  2. Payment
- Increase the size and contrast of the step circles and connecting line.
- Step 1 remains active on this page.
- Step 2 remains inactive but must be clearly readable.
- Both “Delivery Details” and “Payment” labels must use high-opacity text against the teal header.
- Do not make inactive content so faint that it appears disabled or unavailable.
- Progress state must remain programmatically understandable to screen readers.
- Maintain correct active state when navigating between Delivery Details and Payment.

3. DESKTOP GRID AND COLUMN BALANCE

- Use an intentional approximately 56/44 visual balance between the left form column and right order-summary column.
- Maintain a clean, consistent inter-column gap of approximately 28–32 px.
- Keep both columns aligned to the same top baseline beneath the page heading area.
- Keep the right Order Summary sticky if that is current production behavior.
- Avoid excessive empty space between the left form and the summary.
- Do not allow the left column to dominate the page at approximately 65%+ width.

4. INPUT WIDTH AND ALIGNMENT

- Cap visible desktop text-input width at approximately 460–480 px.
- Apply the same width and left alignment to:
  - Recipient name
  - Recipient phone number
  - Sender phone number
  - Comparable single-column fields further down the page
- Do not stretch simple one-line fields across the entire card width.
- The address-collection choice card may remain wider than the text inputs because it is a high-level option.
- At smaller breakpoints, inputs should expand fluidly to the available container width.
- Avoid arbitrary width changes between neighboring fields unless the control type requires it.

5. ADDRESS-COLLECTION OPTION HIERARCHY

- Give the “Ask the recipient for the address” option card a subtle pale-teal background rather than gray or plain white.
- Use a refined teal border consistent with Presentail’s design system.
- Preserve the location icon, explanatory copy, and switch.
- The option card must visually read as a page-level choice that changes the delivery flow, not as another input field.
- Keep the switch’s ON/OFF state obvious and accessible.
- Ensure the full option card is clickable/tappable if compatible with the component implementation.
- Preserve a visible keyboard focus state.

Visible copy remains:
“Ask the recipient for the address”
“We’ll collect the address from the recipient. Delivery time may be impacted if the recipient is unreachable.”

6. SPACING RHYTHM AND GROUPING

- Tighten spacing between closely related fields, especially Recipient name and recipient Phone Number, to approximately 12–16 px between field groups.
- Use larger spacing of approximately 24–32 px between conceptually separate groups:
  - Address-collection choice
  - Recipient contact fields
  - Sender details
  - Location/delivery fields further down the page
  - Preferences
- Use consistent internal card padding, approximately 24 px on desktop unless the design system specifies an equivalent token.
- The page should feel shorter and easier to scan without becoming cramped.
- Preserve comfortable spacing around validation errors and contextual UI.

7. TYPOGRAPHY SYSTEM

Commit to the existing brand serif for meaningful headings:
- Presentail logo
- Delivery Details page heading
- Recipient Details card heading
- Sender Details card heading
- Order Summary heading

Card headings:
- Exact text: “Recipient Details” and “Sender Details”
- Title case, not uppercase/small caps
- Existing elegant Presentail serif
- Approximately 18–20 px
- Medium weight
- Dark Presentail teal
- No horizontal line, divider, or decorative rule beside either heading

Do not use the serif for:
- Field labels
- Input values
- Supporting copy
- Buttons
- Totals
- Product names
- Progress labels

Field hierarchy:
- Labels: approximately 12–13 px, semibold, dark charcoal/teal
- Required markers: clearly visible red, aligned with the label
- Entered values: approximately 15–16 px, regular, near-black
- Empty placeholders: approximately 15 px, regular, clearly lighter cool gray
- Supporting copy: muted but WCAG-compliant

Empty fields must not look populated. Populated values must not look like placeholders.

8. CARD SEPARATION

- Recipient Details and Sender Details must remain two independent cards.
- Each card must have:
  - Its own complete white background
  - Rounded corners matching the existing design system
  - Subtle light-gray boundary and/or soft shadow
  - Its own internal padding
- Show approximately 16–20 px of page background between the two cards.
- The Recipient Details card’s bottom boundary and rounded lower corners must be visible.
- The Sender Details card’s top boundary and rounded upper corners must be visible.
- Do not merge, nest, or visually connect these two cards.
- Do not add a horizontal rule beside either heading.

9. PHONE-NUMBER TOOLTIP COMPATIBILITY

- Preserve the information icon beside the recipient Phone Number label.
- Tooltip remains closed by default.
- Opening the tooltip must not shift the layout.
- Approved tooltip copy when “Ask the recipient for the address” is ON:
  “We’ll only use this number to collect the recipient’s address and coordinate delivery.”
- Do not mention price.
- Ensure the tooltip remains usable with the updated input width and card spacing.
- Follow the keyboard, touch, focus, dismissal, and accessibility requirements from the related task.

10. ORDER SUMMARY

Preserve current content and behavior:
- Product image and name
- Quantity
- Item subtotal
- Delivery charge
- Coupon/discount
- Total
- Delivery window
- Edit cart
- Change delivery
- Continue to Payment CTA
- Secure checkout reassurance

Visual requirements:
- Right column should feel intentionally balanced against the form.
- Keep clear price alignment.
- Preserve the prominent dark-teal CTA.
- Do not redesign pricing or coupon logic in this task.
- Confirm sticky behavior does not obscure content at supported viewport heights.

11. RESPONSIVE BEHAVIOR

Desktop:
- Use the approved two-column balance.
- Capped form controls.
- Separate cards and visible inter-card gap.

Tablet:
- Allow the grid to rebalance without cramped controls.
- Stack columns when the summary can no longer maintain an accessible minimum width.

Mobile:
- Use a single-column layout.
- Inputs and option cards become full width within safe page margins.
- Preserve separate Recipient and Sender cards.
- Maintain at least 44 × 44 px touch targets.
- Progress indicator and labels remain readable without crowding.
- Header reduction must not make controls difficult to tap.
- Tooltip remains within the viewport.
- Preserve sticky CTA behavior only if it does not hide validation messages or essential form content.

RTL / Arabic:
- Validate mirrored alignment, progress direction, icon placement, input behavior, and tooltip positioning.
- Card separation and spacing must remain identical in visual weight.

12. ACCESSIBILITY

- Meet WCAG AA contrast for headings, labels, secondary copy, progress labels, borders where semantically meaningful, and controls.
- Preserve visible focus states for all interactive elements.
- Do not communicate progress state or switch state through color alone.
- Maintain semantic heading order.
- Ensure serif headings remain text, not images.
- Preserve screen-reader labels for the phone tooltip icon and address switch.
- Verify zoom at 200% without clipping or overlapping.
- Respect reduced-motion preferences if any header/progress transition is animated.

13. IMPLEMENTATION GUIDANCE

- Use existing design-system tokens and shared components wherever possible.
- Add new spacing, color, or typography tokens only when no suitable token exists.
- Avoid page-specific magic numbers if shared checkout primitives can support the design.
- Keep visual changes isolated from checkout business logic.
- Preserve form state, validation, payloads, analytics, and navigation.
- Do not change backend contracts in this task.
- Coordinate with the related recipient-name/tooltip task to avoid duplicate component changes or merge conflicts.

ACCEPTANCE CRITERIA

- Checkout header is visibly shorter while remaining accessible.
- Step 1 and Step 2 labels are both clearly legible.
- Step 1 remains visually and semantically active.
- Address-collection option uses a subtle pale-teal background and reads as a high-level choice.
- Desktop columns are visibly balanced at approximately 56/44.
- Visible text inputs use a consistent capped width and left alignment.
- Recipient name and phone are more tightly grouped than separate conceptual sections.
- Page uses larger spacing between address choice, contact, sender, location, and preference groups.
- “Recipient Details” and “Sender Details” use title-case serif headings.
- No horizontal line appears next to either card heading.
- Field labels, values, and placeholders are visually distinct.
- Recipient Details and Sender Details remain two clearly separate cards.
- A visible page-background gap exists between those cards.
- The information icon remains beside recipient Phone Number, with tooltip closed by default.
- The tooltip copy never mentions price.
- Order-summary content, pricing, delivery details, and CTA remain functionally unchanged.
- Desktop, tablet, mobile, Safari, Chrome, and RTL states pass visual QA.
- Checkout validation, Continue to Payment, navigation back, and form persistence work without regression.
