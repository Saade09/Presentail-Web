PHASE 4 — IMPLEMENT THE INTEGRATION

Once the existing authentication system has been identified, implement Sign in with Apple using the authentication provider’s official and current integration method.

Do not implement a parallel custom authentication system when the existing provider already supports Apple.

Examples:

- If the application uses Clerk, configure Apple through Clerk’s supported OAuth connection and use Clerk’s callback flow.
- If the application uses Auth.js / NextAuth, use the Apple provider and the framework’s correct callback endpoint.
- If the application uses another provider, follow that provider’s current implementation pattern.

Implementation requirements:

1. Add a “Continue with Apple” button wherever other login methods appear.

2. Use Apple-compliant wording and styling.

3. Do not use an unofficial Apple logo or a modified Apple mark.

4. Keep existing Google, email and password authentication functioning.

5. Do not expose the Apple private key in:
   - Frontend code
   - Public environment variables
   - Git
   - Logs
   - API responses
   - Browser bundles

6. Store all Apple credentials using Replit Secrets or secure server-side environment variables.

7. Use clear environment variable names. Depending on the framework, these may include:

   APPLE_CLIENT_ID
   APPLE_TEAM_ID
   APPLE_KEY_ID
   APPLE_PRIVATE_KEY

   Only create variables actually required by the authentication library.

8. The APPLE_CLIENT_ID for a website should normally be the Apple Services ID, not the native iOS bundle ID.

9. Correctly format the multiline .p8 private key.

10. Handle private keys entered with escaped line breaks such as:
    \n

11. Never print or log the private key.

12. Implement secure OAuth protections, including:
    - state validation
    - nonce validation where supported
    - secure cookies
    - HTTPS in production
    - server-side token validation
    - correct redirect URI validation

13. Request only necessary scopes:
    - name
    - email

14. Remember that Apple may only provide the user’s name during the first successful authorization. Persist the name when Apple supplies it.

15. On later logins, identify the account using Apple’s stable subject identifier and validated identity token, not merely by display name.

16. Properly support Apple Private Relay email addresses ending in:
    @privaterelay.appleid.com

17. Do not assume that Apple will always return a normal personal email address.

18. Prevent duplicate users where reasonably possible.

19. If the same verified email already exists under Google or email/password login, follow the existing authentication provider’s safe account-linking behavior. Do not invent insecure email-based account linking.

20. Handle cancelled Apple logins gracefully and return the user to the login page with a clear, non-technical message.
