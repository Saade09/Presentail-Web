Context
On product detail pages where free standard delivery and paid express delivery are both available, Express Delivery is currently preselected. In the current Beirut PDP example, this adds a $15 upgrade by default even though the page communicates that standard delivery is included for free.

Example page
https://presentail.com/en-lb/beirut/product/serenity

Problem
Preselecting the paid option can:
• Make the displayed purchase state feel more expensive than the advertised product price.
• Create tension with the “Free standard delivery included” message.
• Be perceived as an involuntary upsell or hidden fee.
• Cause avoidable abandonment before Add to Cart.

Objective
Make free standard delivery the default delivery method whenever it is available. Express delivery must remain clearly available as an optional, customer-initiated upgrade.

Scope
Apply this behavior to product detail pages in every market/storefront where:
1. Free standard delivery is currently available for the product/order; and
2. A paid express option is also available.

Do not force standard delivery where it is unavailable, invalid for the selected product/location/date, or where express is the only eligible method.

Required behavior

1. Initial page state
• On first PDP load, select the free standard/scheduled delivery option by default when it is eligible.
• Do not apply or display an express surcharge in the initial purchase state.
• Express must appear unselected.
• Do not rely on the delivery options’ API/display order to determine the default; select by the delivery method’s stable type/ID and eligibility.

2. Standard-delivery scheduling
• Because standard delivery requires a date/time selection, show the standard option as the active method while clearly indicating that the customer still needs to choose a delivery date and time.
• Do not automatically open a blocking modal on page load.
• Clicking the active standard card, its date/time control, or the CTA while scheduling is incomplete should open/focus the date-and-time picker.
• Do not allow Add to Cart until a valid standard delivery window has been selected.
• The incomplete state must be explicit, e.g. “Choose delivery date and time.”

3. Express upgrade
• Selecting Express Delivery must be an explicit customer action.
• Once selected, apply the configured express fee exactly once.
• Show the fee beside the express option using the market’s currency and existing localization rules.
• If the customer switches back to standard delivery, remove the express fee immediately.
• The selected delivery service sent to cart/checkout must match the visible selected option.

4. Eligibility and fallback
• If free standard delivery is unavailable, preserve the existing valid fallback/default behavior.
• If express is the only eligible method, it may be selected automatically.
• If standard becomes invalid after a location, product, variant, quantity, or delivery-window change, prompt the customer to choose another eligible method; do not silently add a paid upgrade.
• Preserve an explicit customer selection during normal component re-renders. Re-evaluate it only when eligibility changes.
• If a previously selected method is no longer valid, display a clear message before changing the purchase state.

5. Pricing integrity
• Initial price calculations must exclude the express fee when standard is the default.
• Cart, mini-cart, checkout, order payload, and confirmation must not contain an express fee unless Express was explicitly selected.
• Switching between methods repeatedly must never duplicate or retain a stale delivery charge.
• Server-side/cart validation must agree with the PDP state; the UI change alone is not sufficient.

6. Responsive and accessibility requirements
• Implement the same default and switching behavior on desktop and mobile.
• Selected, unselected, incomplete, hover, focus, and disabled states must remain visually distinct.
• Radio controls/cards must be keyboard operable.
• Use correct radio-group semantics and accessible labels.
• Screen readers must announce the selected method, delivery price, and any required date/time action.

Analytics
Track or verify the following events/fields:
• delivery_method_defaulted with method = standard
• delivery_method_selected with method = standard|express and source = user
• delivery_scheduler_opened
• delivery_window_selected
• express_upgrade_selected
• add_to_cart with selected delivery method and delivery fee

Avoid firing a customer-selection event for the automatic default state. If equivalent events already exist, extend the existing schema rather than creating duplicates.

Acceptance criteria
1. Given both free standard and paid express are eligible, when a customer opens a PDP, then standard delivery is visibly selected and the express fee is not applied.
2. Given standard is selected but no window has been chosen, Add to Cart cannot submit an invalid cart and the customer is directed to choose a date/time.
3. Given a valid standard window is selected, Add to Cart sends the standard delivery service and a zero standard-delivery charge.
4. Given the customer explicitly selects Express, the configured express fee is applied once and the cart receives the express service.
5. Given the customer switches from Express back to standard, the express fee is fully removed before Add to Cart.
6. Given standard is unavailable, the PDP selects or requests an eligible method without presenting standard as available.
7. The state remains correct after variant/quantity changes, location changes, hydration, and component re-renders.
8. The behavior passes on desktop and mobile for supported browsers and locales.
9. No regression occurs in cart totals, checkout delivery selection, or order creation.

QA test matrix
• Both methods eligible: initial load
• Standard only
• Express only
• Standard selected, no date/time
• Standard selected with valid date/time
• Express selected
• Express → standard
• Standard → express → standard
• Product variant and quantity changes
• Recipient/delivery location change
• Standard method becomes unavailable after selection
• Page refresh and client hydration
• Back navigation from cart to PDP
• Mobile and desktop
• English and Arabic/RTL where applicable
• Market-specific currencies and configured express fees
• Keyboard-only and screen-reader navigation
• Cart, mini-cart, checkout, and order payload verification

Definition of done
• Implementation reviewed and merged.
• Automated unit/integration tests cover default selection, switching, fee removal, and eligibility fallback.
• End-to-end test verifies PDP → cart behavior for standard and express.
• QA signs off on the matrix above in staging.
• Analytics events/fields are verified in the staging debugger.
• Before/after screenshots or a short recording are attached to the task.
• Release is monitored for add-to-cart rate, checkout completion, express-upgrade rate, delivery-fee errors, and customer-support complaints.

Success metrics
Primary: PDP add-to-cart rate and checkout completion rate.
Guardrails: express upgrade rate/revenue, delivery margin, delivery-method errors, and customer-support contacts related to unexpected fees.

Rollout recommendation
Release behind a feature flag if available. Start with Beirut/Lebanon traffic, validate pricing and order payloads, then expand to other eligible markets after QA and early metric review.
