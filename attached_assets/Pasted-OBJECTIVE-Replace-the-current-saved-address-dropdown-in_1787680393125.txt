OBJECTIVE

Replace the current saved-address dropdown in checkout with a clearer, responsive saved-address experience that reduces duplicated fields and works consistently on mobile web and desktop web.

The implementation must cover:
1. The selected saved-address summary state.
2. The “Change” address chooser on mobile web.
3. The “Change” address chooser on desktop web.
4. Redirecting users to the existing dedicated address collection/editing flow when they add or edit an address.

APPROVED DESIGN DIRECTION

A. Selected saved-address state

- When a saved address is active, replace the “Use a saved address” dropdown plus duplicated standalone recipient fields with one clear selected-details card.
- Card content:
  - Saved address label, e.g. “Mom’s House”.
  - “Default” badge when applicable.
  - Location/district/governorate summary.
  - Recipient name.
  - Recipient phone number.
  - Selected/check indicator.
  - “Edit recipient details” action.
- Show a single “Change” action in the Recipient Details header.
- Do not also show “Use a different address”; it is redundant with “Change”.
- The card is a summary, but the full saved address data must continue to populate the checkout/order payload.
- If the address is already saved, do not show “Save this address to my profile”.
- Preserve all other checkout sections, the selected delivery method, totals and sticky checkout actions unless the newly chosen address changes delivery eligibility.

B. Mobile-web “Change” interaction

- On mobile web, clicking “Change” opens a responsive bottom-sheet-style web dialog.
- This is a website component, not a native-app component.
- Sheet content:
  - Title: “Choose an address”.
  - Supporting copy: “Select a saved address for this delivery.”
  - Close control.
  - List of saved addresses.
  - Current address visibly selected.
  - “Default” badge where applicable.
  - Recipient name, phone and location on each row.
  - “Edit” action per saved address.
  - “Add a new address” action.
  - Sticky primary CTA: “Use this address”.
- The entire address row must be selectable, not only the radio control.
- Selecting a row updates the temporary selection; do not apply it until “Use this address” is pressed.
- Closing the sheet without confirming must keep the original address unchanged.
- Use a fixed web-dialog implementation with dynamic viewport units so it behaves correctly with Safari’s expanding/collapsing browser bars.
- Respect iPhone safe areas using env(safe-area-inset-bottom).
- Lock background page scrolling while open.
- If the address list is long, scroll the list inside the sheet while keeping the heading and confirmation CTA accessible.
- Browser Back should close the open sheet first rather than leave checkout.
- Tapping the backdrop may close the sheet only when no unconfirmed destructive change is involved.

C. Desktop-web “Change” interaction

- On desktop/tablet widths, clicking “Change” opens the same chooser as a centered modal dialog, not a bottom sheet.
- Recommended width: approximately 600–640 px with a sensible max-width and responsive gutters.
- Apply a restrained backdrop overlay so checkout context remains recognizable.
- Close the old floating dropdown implementation behind the modal.
- Modal content and selection behavior must match mobile:
  - “Choose an address” title.
  - Saved address list.
  - Selected/default states.
  - Per-address “Edit”.
  - “Add a new address”.
  - “Use this address”.
- Footer layout on desktop:
  - “Add a new address” as the secondary action.
  - “Use this address” as the primary action.
- Preserve the Order Summary, checkout form, product/pricing information and Continue to Payment state behind the modal.

D. Add and edit address behavior

- “Add a new address” must redirect to the existing dedicated address collection flow; do not recreate the full address form inside this chooser.
- “Edit” must redirect to the existing dedicated edit-address flow for the selected saved record.
- Preserve checkout/cart state before redirecting.
- After the user successfully saves:
  - Return them to checkout.
  - Select the newly added/edited address.
  - Refresh the recipient/address summary.
  - Revalidate delivery eligibility and selected slot.

DATA MAPPING

When a saved address is confirmed, populate every available field from the saved record, including:
- Saved-address ID.
- Address label.
- Default flag.
- Recipient name.
- Recipient phone number and country code.
- Country.
- Governorate/emirate.
- District/city.
- Full delivery details.
- Building/landmark information.
- Coordinates/pin when available.
- Any other delivery notes already stored on the address.

Do not overwrite unrelated checkout data.

DELIVERY BUSINESS RULES

- Recalculate delivery availability and fees only after the user confirms the new address.
- If the new district/governorate makes the existing delivery slot invalid, trigger the already-approved district-change notification and require delivery reselection.
- Related existing Asana task: ✓ Checkout: Notify and require delivery reselection when district change invalidates the selected slot
- If the address does not affect delivery eligibility, preserve the selected slot and do not interrupt the user.
- Never silently change a selected delivery slot without clearly notifying the customer.

REQUIRED STATES

Implement and test:
- No saved addresses: keep the normal editable checkout form and provide a route to add an address.
- One saved address: show it selected plus “Add a new address”.
- Multiple saved addresses.
- Default and non-default addresses.
- Address currently selected.
- Temporary new selection not yet confirmed.
- User cancels/closes the chooser.
- Loading state while addresses are fetched.
- Empty state.
- Fetch failure with retry.
- Address becomes unavailable/deleted.
- Add-address return flow.
- Edit-address return flow.
- District change invalidates selected delivery.
- Long address labels/content wrapping.
- Long address lists with internal scrolling.

RESPONSIVE AND VISUAL REQUIREMENTS

- Follow the attached approved mobile and desktop mockups.
- Preserve Presentail’s current typography, dark-teal palette, borders, radii and shadows.
- Maintain consistent 16 px mobile gutters.
- Minimum touch target: 44 × 44 px.
- Do not allow the dialog to collide with the mobile sticky checkout bar or Safari browser controls.
- No horizontal overflow at any supported viewport.
- Do not introduce native-app-only APIs or behaviors.
- Support English, French and Arabic, including RTL layout and translated text expansion.

ACCESSIBILITY

- Implement with accessible dialog semantics.
- Set aria-labelledby and aria-describedby.
- Trap keyboard focus while open.
- Move focus into the dialog on open and return focus to “Change” on close.
- Support Escape on desktop.
- Radio/selection controls must have accessible labels.
- Ensure selected, hover, focus and disabled states are visually distinguishable.
- Ensure overlay and text contrast meet WCAG AA.
- Avoid relying on color alone to communicate selection.

ANALYTICS

Track at minimum:
- saved_address_change_opened
- saved_address_selected
- saved_address_change_confirmed
- saved_address_change_cancelled
- saved_address_add_new_clicked
- saved_address_edit_clicked
- saved_address_delivery_invalidated

Include address ID and checkout country/district where permitted; do not send full addresses or phone numbers to analytics.

ACCEPTANCE CRITERIA

1. Given a customer has a saved address selected, when checkout loads, then one compact saved-details card is shown and recipient name/phone inputs are not redundantly displayed.
2. Given the customer clicks “Change” on mobile web, then an accessible bottom sheet opens without navigating away or moving the background page.
3. Given the customer clicks “Change” on desktop web, then a centered modal opens instead of the old dropdown.
4. Given another address is selected but not confirmed, when the dialog is closed, then the original address remains active.
5. Given another address is selected and “Use this address” is pressed, then the saved data populates checkout and the summary updates.
6. Given the confirmed address changes delivery eligibility, then the existing district-change/reselection warning is triggered before checkout can proceed.
7. Given “Add a new address” or “Edit” is pressed, then the user is routed to the dedicated address flow and returns to checkout with cart state intact.
8. The solution works on current iOS Safari, Android Chrome, desktop Chrome and desktop Safari.
9. English, French and Arabic/RTL are supported.
10. All attached visual references are followed, with no floating menu overlapping form controls.
