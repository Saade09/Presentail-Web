# Presentail Lebanon — Expo Mobile App

A luxury flower and gift delivery app for Lebanon, UAE, and Cyprus, with an accompanying web storefront. Mobile (Expo) + Web (React/Vite) + API server (Express) in a pnpm monorepo.

## Run & Operate

- `pnpm run typecheck` / `pnpm run build`: full workspace typecheck / build.
- `pnpm run typecheck:libs`: rebuild composite lib `.d.ts` files. Run this if `tsc -p artifacts/<x>` reports phantom errors about missing properties on schema/lib types — it almost always means the cached `lib/*/dist/*.d.ts` is stale.
- `pnpm --filter @workspace/api-spec run codegen`: regenerate API hooks and Zod schemas from the OpenAPI spec.
- `pnpm run check-codegen` (alias: `pnpm --filter @workspace/api-spec run check-codegen`): regenerates codegen outputs and exits non-zero if `git diff` detects drift in `lib/api-client-react/src/generated` or `lib/api-zod/src/generated`. Run before opening a PR whenever `lib/api-spec/openapi.yaml` is modified to catch stale generated files before CI does. To wire this as a git pre-push hook: `cp .husky/pre-push .git/hooks/pre-push && chmod +x .git/hooks/pre-push`.
- `pnpm run check-hardcoded-strings`: runs all three hardcoded-string checkers (mobile, web, API) and fails on any user-visible literal that is not wrapped in a translation call or annotated with `// i18n-ignore`. The `.husky/pre-commit` hook runs this **and** `check-translations` (unused/missing/copy-paste keys) **and** `check-nap-consistency` (phone/email sync between Contact.tsx and locationData.mjs) so all three checks fire before every commit: `cp .husky/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit`.
- `pnpm --filter @workspace/scripts run check-occasion-coverage`: compares occasions in the Presentail OS catalog against the `OCCASIONS` array in `artifacts/presentail-web/src/pages/Shop.tsx` and the `shop.occ.*` translation keys in `artifacts/presentail-web/src/locales/shop.ts`. Runs two checks: (1) a static check that every OCCASIONS entry has a matching translation key in shop.ts (no env vars needed); (2) a live OS catalog check that every occasion slug returned by the OS `/api/occasions` endpoint has an OCCASIONS entry and a translation key — when a slug is missing either, the web storefront shows a raw hyphenated heading like "New Born" instead of the correct translated title. The OS catalog check is skipped with a notice (exit 0) when `PRESENTAIL_OS_API_KEY` is not set. Requires `PRESENTAIL_OS_API_URL` (defaults to `https://os.presentail.com`) and `PRESENTAIL_OS_WORKSPACE` (defaults to `"presentail"`).
- `pnpm --filter @workspace/scripts run check-low-contrast-text`: scans `artifacts/presentail-web/src/` for Tailwind opacity-modifier patterns that push text or UI-component contrast below WCAG AA thresholds (`text-muted-foreground/<N>` at any opacity; `text-foreground/<N>` with N ≤ 60). Annotate a line with `// contrast-ok: <reason>` (or a `{/* contrast-ok */}` JSX comment on the preceding line) to mark a legitimate exception — disabled/inactive UI components (WCAG 1.4.3), purely decorative icons, or hover/focus-only states. Run locally before opening a PR to catch new low-contrast text before Lighthouse does.
- `pnpm --filter @workspace/scripts run check-city-similarity`: compares the prerendered HTML for every pair of same-country city pages (26 LB, 7 AE, 4 CY) using Jaccard similarity on word tokens. Fails when any pair within the same country exceeds 80% similarity — meaning city-specific content is missing and Google may treat them as thin duplicates. Runs in the "Web serve checks" CI workflow. No network calls or build output needed. Script: `scripts/src/checkCitySimilarity.ts`.
- `pnpm --filter @workspace/scripts run check-low-contrast-text-mobile`: scans `artifacts/presentail/` (all `.tsx`/`.ts` source files, skipping `dist`/`dist-web-review`/`static-build`) for React Native StyleSheet and inline-style patterns that produce text contrast below WCAG AA (4.5:1). Three checks: (1) `color: rgba(R,G,B,alpha)` where the base colour is dark/grey (R≤160, G≤160, B≤160) and the effective alpha-composited contrast against white falls below 4.5:1; (2) same-line `color: colors.mutedForeground` (or `subtitle`/`subtext` token) combined with `opacity < 0.7`; (3) near-white `color: rgba(R,G,B,alpha)` where R≥200, G≥200, B≥200 (white/light text on dark backgrounds) — evaluated against the known dark header background tokens from `constants/colors.ts` (`teal900 #00414E`, `teal800 #0a5663`, `charcoal #1A2226`) and flagged if the blended colour falls below 4.5:1 on any of them. Non-text colour properties (`backgroundColor`, `borderColor`, `tintColor`, `shadowColor`, `android_ripple`, etc.) are excluded from matching. Annotate the same line with `// contrast-ok: <reason>` to suppress a violation — valid reasons: disabled/inactive UI (WCAG 1.4.3), decorative icons/non-text UI components where the 3.0:1 SC 1.4.11 threshold applies and is met, press-only states. Script: `scripts/src/checkLowContrastTextMobile.ts`.
- `pnpm --filter @workspace/scripts run check-legacy-domain`: repo guard that fails if the retired `new.presentail.com` domain is reintroduced anywhere in production source (scans all `.ts/.tsx/.js/.mjs/.json/.yml/.html/.css` etc.; excludes `node_modules`, build output, `attached_assets/`, `.agents/`, `.local/`, and Markdown docs). The canonical storefront domain is `presentail.com` — reintroducing the old subdomain silently breaks "Continue with Apple", Apple Pay, and rich link previews. For a genuinely legitimate reference (e.g. a test asserting the old domain is absent) add a trailing `// allow-legacy-domain` comment. Runs in CI as a step in the `check-translations` GitHub Actions workflow on every PR touching mobile/web/api/lib/scripts.
- `pnpm --filter @workspace/scripts run check-translations`: validate the mobile and web translation catalogues before opening a PR — checks for unused keys, missing AR/FR translations, copy-pasted (untranslated) values, empty values, orphan locale keys, and undefined key references. Run this locally to catch CI failures early. Add `--verbose` to list every scanned source file. See the header comment in `artifacts/presentail/lib/translations.ts` for the mobile catalogue workflow and the `// no-translate` annotation convention for brand names and loan words. See the header comment in `artifacts/presentail-web/src/locales/index.ts` for the web catalogue workflow (same one-commit rule: add EN + AR + FR together; short brand names under 25 chars are auto-skipped by the copy-paste check).
- `pnpm --filter @workspace/scripts run check-nap-consistency`: verifies that the phone and email in `artifacts/presentail-web/src/lib/locationData.mjs` (the JSON-LD local-business schema source) match the `PHONE_E164` and `SUPPORT_EMAIL` constants in `Contact.tsx` for all three countries (LB, AE, CY). Fails with a diff when they diverge so search engines never see a stale phone/email in structured data while the contact page shows something different. Also runs automatically via the `.husky/pre-commit` hook — re-enable it with `cp .husky/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit`.
- `pnpm --filter @workspace/db run push`: push DB schema changes to the **development** database. **Production migrations are automated via two layers**: (1) The API server's `artifact.toml` production build step runs `pnpm --filter @workspace/db run push-force` before `pnpm --filter @workspace/api-server run build` — so every Replit publish applies the schema first and the deploy is aborted (old server keeps running) if migration fails. `DATABASE_URL` must be set as a Replit secret for this to connect. (2) The `DB – Apply schema to production` GitHub Actions workflow (`.github/workflows/db-migrate-prod.yml`) additionally runs `push-force` automatically whenever `lib/db/**` lands on `main` — this acts as a pre-publish safety net. The workflow requires a `PROD_DATABASE_URL` GitHub secret (set in GitHub → Settings → Secrets → Actions; scoped to the `production` environment for an optional manual-approval gate). To trigger it manually: GitHub → Actions → "DB – Apply schema to production" → Run workflow → set "Confirm you want to push" to true. In an emergency you can still run directly: `DATABASE_URL=<prod-url> pnpm --filter @workspace/db run push-force`.
- `pnpm --filter @workspace/presentail-web run check-chunk-budget`: print a per-chunk size report (raw + Brotli, instant vs on-demand) and fail if any JS chunk exceeds 200 kB Brotli-compressed. Run after `pnpm --filter @workspace/presentail-web run build`. Also runs automatically in the "Web serve checks" CI workflow so regressions are caught on every PR.
- `pnpm --filter @workspace/presentail-web run check-public-image-budget`: scan **all** images under `artifacts/presentail-web/public/` (logos, app icons, OG default, catalog thumbnails, blog heroes, marketing images) and fail if any exceeds its per-format byte budget. Budgets (`FORMAT_BUDGET_KB` in the script): photographic formats `.webp`/`.avif` ≤700 kB, `.jpg`/`.jpeg` ≤300 kB; icon-ish `.png`/`.gif`/`.bmp`/`.tiff` ≤256 kB, `.svg`/`.ico` ≤64 kB. The stricter blog rule is folded in: files under `public/blog/` are capped at 300 kB and must be WebP (no PNG/BMP/TIFF — they're embedded in share-link previews). Documented legacy exceptions live in the script's `ALLOWLIST` (currently the two unreferenced `hero-bouquet*.png` exports — delete or re-encode them rather than keep). No build required — checks source files directly. Runs in the "Web serve checks" CI workflow before the unit tests so a heavy asset fails the PR early. Re-encode offenders with e.g. `cwebp -q 80 image.png -o image.webp`.
- `pnpm --filter @workspace/presentail-web run generate-og-image`: regenerate the default Open Graph share image (`public/opengraph.jpg`, 1200×630 JPEG). Run this whenever the Presentail wordmark or brand colours change. The committed file is served verbatim as the fallback `og:image` for any page that has no per-entity OG image. Script: `artifacts/presentail-web/scripts/generate-og-image.mjs`.
- `pnpm --filter @workspace/presentail-web run generate-blog-hero-variants`: generate the responsive WebP variants (`<slug>-480.webp`, `<slug>-768.webp`) for every blog hero in `artifacts/presentail-web/public/blog/`. Uses `sharp` (already a devDependency) to downscale each original `<slug>.webp`; idempotent — a variant is only (re)generated when missing or older than its original, and widths ≥ the original's intrinsic width are skipped (no upscaling). Variant widths live in the single source of truth `artifacts/presentail-web/blog-hero-variants.config.mjs` (`BLOG_HERO_VARIANT_WIDTHS = [480, 768]`), a dependency-free module re-exported by `blog-hero-variants.mjs` (for the node scripts) and imported directly by `Blog.tsx`/`BlogPost.tsx` (so the browser bundle never pulls in `node:` builtins). Both components derive their `buildSrcSet()` widths from this constant — `Blog.tsx` passes the full array, `BlogPost.tsx` passes `[Math.max(...BLOG_HERO_VARIANT_WIDTHS)]` — so the rendered `srcset`, the generator, and the CI check can never drift apart. **Runs automatically as the first step of the web `build` script**, so a normal build always produces the variants. Contributor flow for a new/replaced hero: drop the `<slug>.webp` into `public/blog/`, run this script (or any build), and commit the generated variant files.
- `pnpm --filter @workspace/presentail-web run check-blog-hero-variants`: CI guard that fails if any committed blog hero is missing its `<slug>-480.webp`/`<slug>-768.webp` variant (or a variant is the wrong size). Parses the WebP header directly (no image library needed), so it's a fast standalone check on source files. Runs in the "Web serve checks" CI workflow right after `check-public-image-budget`. A failure means a hero was added/replaced without (re)generating variants — run `generate-blog-hero-variants` and commit the result. Without committed variants the `srcset` 404s the missing widths and the browser silently falls back to the full-resolution original, quietly undoing the page-speed win.
- `pnpm --filter @workspace/presentail-web run check-stripe-isolation`: assert that no Stripe library symbols appear in the app-entry instant closure or the checkout-initial closure (chunks statically reachable from `src/pages/Checkout.tsx`). Patterns checked: `js.stripe.com` (CDN URL injected by @stripe/stripe-js) and `StripeProvider` (React context from @stripe/react-stripe-js). `loadStripe` and `@stripe/` are intentionally excluded — they legitimately appear in the Checkout chunk as dynamic-import call-site strings and are not indicators of a bundling regression. Run after `pnpm --filter @workspace/presentail-web run build`. Also runs in CI (`chunk-budget` job). A failure means Stripe library code crept into a chunk that loads before the user selects a card payment method; fix it by ensuring every `@stripe/` import is behind a `React.lazy()` boundary or a dynamic `import()` and that the `vendor-stripe` manualChunks rule is intact in `vite.config.ts`.
- `pnpm --filter @workspace/presentail-web run test:e2e`: run Playwright end-to-end tests. In the Replit container the `chromium` Nix system package is installed and the script auto-detects it via `command -v chromium`, so no extra setup is needed — just run the command. The `playwright.config.ts` reads `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` and passes it as `executablePath` only when the env var is set; when it is empty (e.g. in GitHub Actions CI where Playwright downloads its own browser), the downloaded browser is used instead. To override manually: `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/path/to/chromium pnpm --filter @workspace/presentail-web run test:e2e`.
- `pnpm --filter @workspace/api-server run dev`: run API server locally.
- `GET /api/admin/funnels` (admin HTML page; paste `PUSH_ADMIN_TOKEN` once and it's cached in localStorage) and `GET /api/admin/funnels/data?days=N` (JSON, header `x-push-admin-token: $PUSH_ADMIN_TOKEN`, `days` capped at 30, default 14): per-day per-platform purchase funnel (cart→checkout→payment→order) plus per-(platform, surface) login-prompt funnel. Reuses `aggregateBuckets` from the alerter monitors so the dashboard and Slack alerts can never disagree.
- `GET /api/auth/diagnostics` (admin-only, header `x-push-admin-token: $PUSH_ADMIN_TOKEN`): pings the two upstreams `/api/auth/exists` depends on (WC `/customers` + WP `/jwt-auth/v1/token`) and runs the classifier against a guaranteed-not-to-exist email. Returns `{ ok, checks: { wcCustomers, wpJwtPlugin, classifier } }` so ops can verify a regression in seconds — use this when shoppers report being routed to sign-up despite already having an account, or when the auth-exists lookup monitor pings Slack.
- `pnpm --filter @workspace/scripts run import-customers-to-clerk`: import existing local customer rows into Clerk so returning shoppers signing in via Clerk are matched to their existing customer row by email. See script header for flags. Idempotent. Requires `CLERK_SECRET_KEY`, `DATABASE_URL`.
- **Promote a TestFlight build to the App Store**: GitHub → Actions → "iOS – Promote TestFlight build to App Store". Two-step flow recommended (`mode=dry-run` to preview the per-locale notes & subtitle in the job summary, then re-run with `mode=submit`). Subtitle lives in `artifacts/presentail/app-store-metadata.json` (≤30 chars). On successful `submit` the workflow auto-bumps `expo.version` via `pnpm --filter @workspace/scripts run bump-app-version` and opens a PR. Full behaviour and inputs documented in `.github/workflows/ios-app-store.yml` and `scripts/src/promoteToAppStore.ts`.

**Required Environment Variables**:
- Presentail OS (primary catalog + order submission): `PRESENTAIL_OS_API_URL`, `PRESENTAIL_OS_API_KEY`. All product listings, categories, occasions, brands, and new orders are submitted to Presentail OS. `PRESENTAIL_OS_API_KEY` must have write permissions (the `POST /api/orders` endpoint requires it). `PRESENTAIL_OS_WORKSPACE` defaults to `"presentail"`.
- WooCommerce (deprecated — mobile JWT auth only): `WC_CONSUMER_KEY`/`WC_CONSUMER_SECRET` (LB), `WC_DUBAI_*`, `WC_ABUDHABI_*`, `WC_CYPRUS_*`. No longer used for product data or order submission. Only WordPress JWT auth (`/jwt-auth/v1/token`) still depends on these for mobile login until a Presentail OS auth endpoint is available.
- CyberSource Unified Checkout (Lebanon USD card payments): `CYBERSOURCE_MERCHANT_ID` (Business Center Merchant ID), `CYBERSOURCE_API_KEY_ID` (REST API key ID), `CYBERSOURCE_SHARED_SECRET_KEY` (base64-encoded HMAC-SHA256 shared secret from Business Center → Payment Configuration → Key Management → REST Shared Secret), `CYBERSOURCE_ENVIRONMENT` (`"test"` for apitest.cybersource.com or `"live"` for api.cybersource.com; defaults to `"test"`). When any of the first three are unset, `POST /api/payment/cybersource/capture-context` returns 503 and the tile is invisible to shoppers (the UI hides it when the capture-context call fails). CyberSource is gated to Lebanon (`countryCode === "LB"`) + USD-display-currency shoppers only on both web and mobile.
- Push & sync: `PUSH_ADMIN_TOKEN`; optional `WOO_SYNC_ENABLED`, `WOO_SYNC_INTERVAL_MS` (default 900000, min 60000), `WOO_SYNC_PUSH_ON_CHANGE`. `BANNERS_REMOTE_URL` is **retired** — homepage banners are now updated exclusively via the OS `banner.updated` webhook event. `PRESENTAIL_OS_WEBHOOK_SECRET` is the HMAC-SHA256 signing secret for all OS webhook events (verify by computing `HMAC-SHA256(secret, "{delivery-id}.{timestamp}.{rawBody}")` and comparing to the `sha256=` prefix in `x-presentail-signature`; requests older than 5 minutes are rejected). When unset, `POST /api/os/webhook` returns 503 so it is never an open unauthenticated trigger.
- Order confirmation / delivery emails (optional — off when `SMTP_HOST` is unset): `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_SECURE` (`"true"` for port-465 TLS), `SMTP_USER`, `SMTP_PASS`. `EMAIL_FROM` = sender address (e.g. `orders@presentail.com`; falls back to `SMTP_USER`). `EMAIL_NOTIFY_STATES` = comma-separated `OrderState` values that trigger an email (default `confirmed,delivered`). Customer email is looked up from the `customers` table via the order's `customer_id`; guest orders with no email are silently skipped. Failures log a WARN and record an `email_notify_failed` analytics event — they never block the webhook response.
- SMS/WhatsApp delivery updates (optional — off when unset): `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM` (default sender: E.164 number, Messaging Service SID, or alphanumeric ID). Per-country overrides: `TWILIO_FROM_LB` (Lebanon), `TWILIO_FROM_AE` (UAE), `TWILIO_FROM_CY` (Cyprus). WhatsApp: `TWILIO_WHATSAPP_FROM` (e.g. `whatsapp:+14155238886`). `SMS_CHANNEL` = `sms` | `whatsapp` | `both` (default `sms`). `SMS_NOTIFY_STATES` = comma-separated OrderState values that trigger a message (default `out_for_delivery,delivered`). `SMS_TRACKING_URL_BASE` = base URL for the tracking link in the message body (default `https://presentail.com/orders`). The billing phone is stored on the `app_orders` row (`sender_phone`) when an order is recorded, so SMS triggers on `POST /api/push/order-event` without a WooCommerce round-trip.
- SEO health digest (optional): `SEO_AUDIT_MONITOR_ENABLED` (default on) — runs once per UTC day, audits 7 key pages (LB/AE/CY homepages, product, brand, category, occasion), and fires a Slack alert via `ALERTS_SLACK_WEBHOOK_URL` when any page has a missing, unreachable, or fallback-only OG image. Set to `"0"` / `"false"` / `"no"` / `"off"` to disable. No other env var is required; the page list is hardcoded in `artifacts/api-server/src/lib/seoAuditMonitor.ts`.
- Merchant Listing suggestions digest (optional): `MERCHANT_LISTING_SUGGESTIONS_MONITOR_ENABLED` (default on) and `GOOGLE_RICH_RESULTS_API_KEY` (Google API key with Search Console API enabled). Runs once per ISO week; calls the Google Rich Results Test API for up to 9 representative product page URLs (3 slugs × LB/AE/CY), extracts SUGGESTION-level issues from the Products rich-result type, deduplicates them by issue message, and posts a grouped Slack digest via `ALERTS_SLACK_WEBHOOK_URL`. No-op when either `GOOGLE_RICH_RESULTS_API_KEY` or `ALERTS_SLACK_WEBHOOK_URL` is unset. Monitor: `artifacts/api-server/src/lib/merchantListingSuggestionsMonitor.ts`.
- FX rate fallback monitor (optional): `FX_FALLBACK_MONITOR_ENABLED` (default on), `FX_FALLBACK_CONSECUTIVE_FAILURES_MAX` (default 12 — alert when the live open.er-api.com fetch has failed this many consecutive 5-minute retry cycles, i.e. ≈1 h of failed live-rate fetches). When triggered, fires a Slack alert via `ALERTS_SLACK_WEBHOOK_URL` and logs a WARN on every `/api/fx/rates` response that uses embedded static rates; also records a durable `fx_rates_fallback` analytics event per fallback response (queryable via the `analytics_events` table).
- IP geolocation fallback monitor (optional): `GEO_CURRENCY_FALLBACK_MONITOR_ENABLED` (default on), `GEO_CURRENCY_FALLBACK_COUNT_MAX` (default 50 — alert when ≥ this many `geo_currency_fallback` analytics events are recorded in the prior UTC hour, meaning both ipapi.co and ipwho.is failed to resolve shoppers' IPs to a country and they were silently shown USD prices). Fires a Slack alert via `ALERTS_SLACK_WEBHOOK_URL`. The event is recorded in `analytics_events` by `routes/geo.ts` whenever `source=lookup` and `countryCode=null`; the monitor lives in `artifacts/api-server/src/lib/geoCurrencyFallbackMonitor.ts` and runs hourly.
- Alerting (optional): `ALERTS_SLACK_WEBHOOK_URL` (Slack incoming webhook for ops alerts; falls back to WARN-level logs when unset). Clerk session fallback monitor: `CLERK_SESSION_FALLBACK_MONITOR_ENABLED` (default on), `CLERK_SESSION_FALLBACK_MIN_COUNT` (default 10 — alert when ≥ this many `clerk_session_fallback` events are recorded in the prior UTC day, indicating the Clerk session token template is missing the required fields). Auth-exists lookup monitor: `AUTH_EXISTS_LOOKUP_MONITOR_ENABLED` (default on), `AUTH_EXISTS_MIN_LOOKUPS` (default 50), `AUTH_EXISTS_INCONCLUSIVE_RATE_MAX` (default 0.05). Login-prompt funnel monitor: `CHECKOUT_LOGIN_FUNNEL_MONITOR_ENABLED` (default on), `CHECKOUT_LOGIN_MIN_VIEWED` (default 25), `CHECKOUT_LOGIN_GUEST_RATE_MAX` (0.7), `CHECKOUT_LOGIN_SIGNIN_RATE_MIN` (0.1), `CHECKOUT_LOGIN_DISMISS_RATE_MAX` (0.5). Purchase funnel monitor (cart→checkout→payment→order): `CHECKOUT_PURCHASE_FUNNEL_MONITOR_ENABLED` (default on), `CHECKOUT_PURCHASE_MIN_CART_VIEWED` (default 50), `CHECKOUT_PURCHASE_CART_TO_CHECKOUT_MIN` (0.15), `CHECKOUT_PURCHASE_CHECKOUT_TO_PAYMENT_MIN` (0.4), `CHECKOUT_PURCHASE_PAYMENT_TO_ORDER_MIN` (0.3). Social sign-in failure monitor (Google/Apple): `SOCIAL_AUTH_FAILURE_MONITOR_ENABLED` (default on), `SOCIAL_AUTH_MIN_ATTEMPTS` (default 20), `SOCIAL_AUTH_FAILURE_RATE_MAX` (default 0.2), `SOCIAL_AUTH_FAILURE_COUNT_MAX` (default 100 — absolute per-(platform, provider) failure cap, fires even when the rate is fine but volume is huge), `SOCIAL_AUTH_NEW_ERROR_MIN_COUNT` (default 5) and `SOCIAL_AUTH_NEW_ERROR_BASELINE_DAYS` (default 14) for the previously-unseen-error-code detector. Upsell funnel monitor: `UPSELL_FUNNEL_MONITOR_ENABLED` (default on), `UPSELL_FUNNEL_MIN_TAB_CLICKS` (default 20 — skip platform when daily tab clicks are below this), `UPSELL_FUNNEL_ITEM_ADD_RATE_MIN` (default 0.1 — minimum ratio of `upsell_item_added` to `upsell_tab_clicked`; alert when below), `UPSELL_FUNNEL_CHECKOUT_PROCEEDED_MIN` (default 5 — minimum absolute `upsell_checkout_proceeded` count per platform; alert when below), `UPSELL_REVENUE_PCT_DROP_MAX` (default 5 — alert when any platform's prior day's upsell revenue % of total purchase revenue drops more than this many percentage points below that platform's own 7-day trailing average; set to 0 to disable this check while keeping the rest of the monitor active; requires a warm OS product cache to compute estimated upsell revenue; check is now per-platform so a drop on one client build cannot be masked by healthy numbers on another). `UPSELL_REVENUE_PCT_MIN_ORDERS` (default 5 — skip a platform in the revenue % WoW check when it has fewer than this many confirmed orders on the prior day, suppressing noise from low-volume days). Session ID coverage monitor (upsell events): `UPSELL_SESSION_COVERAGE_MONITOR_ENABLED` (default on), `UPSELL_SESSION_COVERAGE_MIN_EVENTS` (default 50 — minimum total `upsell_item_added` events on the evaluated day before the check fires), `UPSELL_SESSION_COVERAGE_MIN_RATE` (default 0.8 — alert when the fraction of events with a non-null `session_id` drops below this). Session ID coverage monitor (funnel events — cart_viewed, checkout_started, order_placed): `FUNNEL_SESSION_COVERAGE_MONITOR_ENABLED` (default on), `FUNNEL_SESSION_COVERAGE_MIN_EVENTS` (default 50 — shared minimum for all three event types), `FUNNEL_SESSION_COVERAGE_MIN_RATE` (default 0.8 — shared minimum coverage rate); per-event-type overrides: `FUNNEL_SESSION_COVERAGE_CART_VIEWED_MIN_EVENTS`, `FUNNEL_SESSION_COVERAGE_CART_VIEWED_MIN_RATE`, `FUNNEL_SESSION_COVERAGE_CHECKOUT_STARTED_MIN_EVENTS`, `FUNNEL_SESSION_COVERAGE_CHECKOUT_STARTED_MIN_RATE`, `FUNNEL_SESSION_COVERAGE_ORDER_PLACED_MIN_EVENTS`, `FUNNEL_SESSION_COVERAGE_ORDER_PLACED_MIN_RATE` (each falls back to the shared FUNNEL_SESSION_COVERAGE_* values when unset). Web vitals monitor: `WEB_VITALS_MONITOR_ENABLED` (default on), `WEB_VITALS_LCP_WARN_MS` (default 4000 — alert when p50 LCP exceeds this), `WEB_VITALS_INP_WARN_MS` (default 500 — alert when p75 INP exceeds this; Google "needs improvement" threshold), `WEB_VITALS_CLS_WARN` (default 0.25 — alert when p75 CLS exceeds this; Google "poor" threshold), `WEB_VITALS_MIN_SAMPLES` (default 20 — skip a metric when fewer samples are available). ## Architecture decisions

- **Multi-store WooCommerce**: API server resolves store config (URL, credentials, currency, country) per request from `countryCode`/`cityId`, with Lebanon as fallback. Server caches are keyed `${baseUrl}::${lang}`; client React Query keys include `countryCode`/`cityId`. WC is now used only for order submission and mobile JWT auth — product data comes from Presentail OS.
- **Presentail OS catalog (Phase 3)**: All product listings, categories, occasions, and brands are served from `os.presentail.com`. The static lib/catalog-data products array has been retired (Phase 3); the static catalog fallback path in the API server has been removed. The `osProductsCache` is the sole in-memory product store. WooCommerce is only consulted for order submission and for the startup window before OS first populates.
- **In-app accounts**: Native sign-in / sign-up / delete using `expo-secure-store` + WordPress JWT / WC REST. Avoids web redirects (smoother UX, Apple-compliant). Clerk handles web auth and is being migrated to mobile. `/auth/exists` checks the local `customers` table first (Phase 3) — local hits skip WC entirely and return `exists_true_local`.
- **WC_AUTH_ENABLED feature flag (Phase 4)**: `WC_AUTH_ENABLED` env var (default `false`) gates all remaining WooCommerce/WordPress auth calls. When unset or falsy: `/auth/login` returns `410 Gone` with code `login_deprecated` (mobile `AuthContext` surfaces a "please update the app" message); `/auth/register` creates a local-only customer row (no WC round-trip); `/auth/exists` treats a local miss as definitive `exists_false`; social sign-in (`issueSocialSession`) skips `syncCustomerToWoo`; `/auth/me` GET resolves via `localCustomerId` JWT claim; `/auth/me` PUT patches the local row by `customers.id`; `/auth/me` DELETE anonymises the local row without touching WC. Set to `"1"` / `"true"` / `"yes"` only during the migration window when old app versions still depend on WP JWT login. Migration log: `wp_customer_id_map` table (see `lib/db/src/schema/wpCustomerIdMap.ts`). Import script: `pnpm --filter @workspace/scripts run import-wc-customers` (requires `DATABASE_URL`, `WC_*` keys, `WP_URL`). Audit script: `pnpm --filter @workspace/scripts run audit-wc-customers`.
- **Push notifications**: Expo Push, server registers/unregisters tokens scoped to user id, an admin-only webhook triggers order-state pushes.
- **Currency**: All `priceValue` is stored in USD (WC base) and converted only at display time via `CurrencyContext` and `data/currencies.ts`.
- **Display currency auto-detection (mobile)**: precedence is manual pick → device GPS → IP → USD. GPS path uses `expo-location` (Lowest accuracy, 4 s timeout) → `GET /api/geo/currency-by-coords` (BigDataCloud, keyless, 0.1° rounded cache, 1 h TTL, 60 req / 15 min). Permission prompt is shown only on the first run (AsyncStorage `@presentail/location-permission-asked-v1`); re-triggerable from the Currency sheet. IP-based `/api/geo/currency` is the silent fallback.
- **Scheduled OS sync (Phase 3)**: `lib/wooSync.ts` polls each store on `WOO_SYNC_INTERVAL_MS`. Each tick: refreshes banners, invalidates the Presentail OS product cache (LB once per tick — OS refetches all countries), reconciles WC customers into local rows (only when WC keys are configured), then sends a silent Expo `data_refresh` push to devices whose persisted `countryCode`/`cityId` maps to that store when OS content has changed. WC product fetching was removed in Phase 3 — change detection is now based solely on OS product hash. `POST /api/woo/sync/run` triggers on demand (gated by `PUSH_ADMIN_TOKEN`).
- **Checkout funnel monitoring**: clients emit lightweight allowlisted analytics events (`AnalyticsEventName` in the OpenAPI spec) for the login prompt and for the broader purchase funnel — `cart_viewed` → `checkout_started` → `payment_method_selected` → `order_placed`. The login-prompt monitor (`lib/checkoutLoginFunnelMonitor.ts`) watches guest / sign-in / dismiss ratios; the sibling purchase monitor (`lib/checkoutPurchaseFunnelMonitor.ts`) computes step-to-step conversion per platform and alerts via Slack when any single step collapses below the configured minimum. Both run hourly, evaluate the previous full UTC day once, and share the `analytics_events` table (the login monitor handles the 30-day prune for both). Mobile emits from `artifacts/presentail/lib/analytics.ts`, web from `artifacts/presentail-web/src/lib/analytics.ts`. Adding a new event name requires an OpenAPI spec change so we never log unbounded user-controlled strings.
- **Locale-aware web URLs**: `/{lang}-{country}/{city}/...` for browse and shop. SEO-injected per-entity OG tags (product / brand / category / occasion) are rendered server-side so WhatsApp / iMessage / Slack get rich previews; see `artifacts/presentail-web/seo-inject.mjs`.

## Gotchas

- **Stale lib `.d.ts`**: composite project references read each lib's emitted `.d.ts`, not its source. After editing `lib/db/src/schema/*` (or any other lib), run `pnpm run typecheck:libs` before trusting `pnpm --filter @workspace/<artifact> run typecheck` — phantom "Property does not exist on type X" errors against schema/lib types are almost always stale dist files.
- **WordPress JWT plugin required**: "JWT Authentication for WP REST API" must be installed on `presentail.com` for login. Without it, login returns `503 jwt_not_installed` (registration still works).
- **Payment return URLs**: Mamo / PayPal need HTTPS, so `GET /api/payment/return` bridges the gateway redirect to the app's deep link `presentail://payment-return`.
- **Currency on the wire**: Order payloads sent to WC also use USD `priceValue`; conversion is display-only.
- **Category filtering**: Homepage categories are filtered by the `PRODUCT_TYPE_SLUGS` allowlist to exclude occasion / colour / recipient categories. `BestSellersPreview` falls back gracefully on empty categories.
- **Stripe `API_BASE`**: `lib/stripe.ts`'s `API_BASE` must be `https://${EXPO_PUBLIC_DOMAIN}` so `/api/...` calls proxy through the same origin.
- **Product detail screen must stay defensive**: `artifacts/presentail/app/product/[slug].tsx` is on the critical purchase path. A synchronous throw during render closes the iOS app before any error boundary catches it (Task #180). Three known fragile spots: (1) `useLocalSearchParams` may return `slug` as an array — coerce before string compare; (2) `product.image` may be `null` / `{ uri: "" }` — only render `<Image>` for a real require'd asset or non-empty `{ uri }`; (3) `product.priceValue` may arrive `NaN` / `undefined` from a stale cart row — gate with `Number.isFinite` before `Math.round` / `formatNative` / `<Price>`. Any new assumption (delivery country, time zone, day list) must have a safe fallback so first render cannot crash.
- **EAS secrets are project-level and cover all platforms**: `EXPO_PUBLIC_*` values needed in production binaries (e.g. `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `EXPO_PUBLIC_GOOGLE_*`) must be registered as EAS secrets — not just Replit secrets — because EAS inlines them into the binary at build time. A single `eas secret:create --scope project --name <KEY> --value <VALUE>` call covers **both iOS (TestFlight/App Store) and Android (Play Store)** production builds automatically; there is no per-platform registration step. To list what is currently registered: `eas secret:list`. If a key is missing when a Play Store or TestFlight build runs, the binary will ship with an empty string for that variable and Stripe / Google sign-in will fail at runtime.
- **Google Sign-In needs an EAS build, not Expo Go**: `@react-native-google-signin/google-signin` is a native module. Required env values must be EAS build-time secrets (`EXPO_PUBLIC_*` are inlined into the binary at build time), not just Replit secrets. After changing any Google client id, trigger a fresh build. `app.config.js` auto-derives the reversed iOS scheme and fails the build if the placeholder would ship.
- **Google Sign-In on Android needs an Android OAuth client + signing SHA-1**: Google's Android SDK matches `(package name = com.presentail.lb, signing SHA-1)` against an Android-type OAuth client. Add SHA-1s for every signing key the binary may carry: local debug keystore, EAS upload keystore, Play Store app-signing key. Add the Android client id to the API server's `GOOGLE_CLIENT_IDS` so `aud` verification accepts those tokens. Symptom of mismatch: `signIn()` resolves with `DEVELOPER_ERROR` (status code 10) immediately after the account picker.
- **iOS bundle localizations must mirror App Store Connect**: `expo.ios.infoPlist.CFBundleLocalizations` in `artifacts/presentail/app.json` (currently `en`, `ar`, `fr`) must equal the localizations enabled on App Store Connect, otherwise App Review flags a mismatch. Adding a locale on ASC alone is not enough — the next EAS build must also declare it.
- **IP-based currency detection**: Replit puts requests through multiple proxy hops, so `req.ip` ≠ the real client IP. `routes/geo.ts` walks `x-forwarded-for` for the leftmost public address (`pickClientIp`) and prefers `cf-ipcountry` when present. Upstream lookup is ipapi.co with ipwho.is as a keyless fallback (without it, ipapi.co's 1000/day quota silently pins everyone to USD). Negative cache is 60 s, positive 1 h. The rate-limiter's `keyGenerator` must wrap the resolved IP through `ipKeyGenerator` (express-rate-limit v8) or IPv6 visitors silently bypass the limit. Don't widen `app.set("trust proxy", 1)` casually — other limiters key off `req.ip`.
- **Clerk dev vs prod keys**: production Clerk keys (`pk_live_…`/`sk_live_…`) are domain-locked to `presentail.com` and won't work on Replit dev preview URLs. Use the development Clerk instance keys (`pk_test_…`) for local/dev, prod keys only for the deployed app. Each Clerk instance also has its own `whsec_…` webhook secret.
- **`/auth/exists` must consult WP users, not just WC customers**: legacy accounts may exist as WordPress users with no matching `wc/v3/customers` row (created before WC was installed, JWT-only registrations, non-`customer` roles). If `/api/auth/exists` only checks WC, returning shoppers get routed to the sign-up step instead of the password-login step. The endpoint falls back to a JWT-plugin probe (`POST /jwt-auth/v1/token` with a deliberately bogus password, inspecting `incorrect_password` vs `invalid_email`/`invalid_username`) and returns `code: "lookup_failed"` / `"lookup_unavailable"` when it can't actually confirm — the mobile auth sheet must treat those codes as errors and show "couldn't check, try again", never silently advance to sign-up. Every outcome is logged + persisted to `analytics_events` (name `auth_exists_outcome`, `action` is the outcome bucket); `lib/authExistsLookupMonitor.ts` evaluates the prior UTC day hourly and Slack-alerts when the inconclusive rate exceeds `AUTH_EXISTS_INCONCLUSIVE_RATE_MAX`. The signup step (`components/auth/SignupStep.tsx`) renders an "I already have an account — sign in" link as a manual escape hatch when the classifier guesses wrong; both `app/auth.tsx` and `components/CheckoutLoginSheet.tsx` wire it back to `passwordLogin`. Use `GET /api/auth/diagnostics` to verify both upstreams in one call.
- **iOS Google Sign-In needs Keychain Sharing entitlement**: `@react-native-google-signin/google-signin` writes its session to the iOS keychain. Without **Keychain Sharing** in the app's entitlements (and the matching capability in the active provisioning profile), `GoogleSignin.signIn()` rejects synchronously with native code `-61440` (`errSecMissingEntitlement`) before the account picker ever appears. `artifacts/presentail/app.json` adds `ios.entitlements["keychain-access-groups"] = ["$(AppIdentifierPrefix)$(CFBundleIdentifier)"]` for this reason — any change to bundle id / signing team requires a fresh EAS build so the entitlement gets re-signed into the binary, and the App ID on Apple Developer must have Keychain Sharing enabled. Symptom of regression: shoppers see "Google sign-in is temporarily unavailable" with `-61440` only in the dev/server log.
- **Web sign-in JIT-creates Clerk users for existing WP shoppers**: `POST /api/auth/web-bridge` is the bridge between the web sign-in page and Clerk. It looks the email up via WC + the WP JWT-plugin probe (same `lookupWpUserByEmail` helper as `/auth/exists`), and if the shopper exists in WP/WC it ensures a matching Clerk user exists (idempotent — `form_identifier_exists` is treated as success). Hard-error contract: when the response includes `code: "lookup_failed"` or `"lookup_unavailable"`, the web SignIn page MUST surface an error and keep the shopper on the email step — silently advancing to sign-up would create a duplicate Clerk account divorced from the WP order history. Mobile `/auth/register` and `/auth/social/{google,apple}` mirror new accounts into Clerk via `mirrorAndPropagateToClerk` (best-effort, fire-and-forget) so a fresh signup shows up in Clerk within seconds. The daily catch-up worker (`lib/clerkCatchupSync.ts`) is a safety net that re-runs the import-customers-to-clerk mapping in-process; it's gated on `CLERK_CATCHUP_SYNC_ENABLED` (default off), runs once per UTC day, caps each pass at `CLERK_CATCHUP_SYNC_MAX_PER_RUN` (default 500), and is a no-op when `CLERK_SECRET_KEY` isn't configured or `NODE_ENV=test`.
- **Native Apple Pay setup (iOS app)**: The `StripeProvider` in `_layout.tsx` already uses `merchantIdentifier="merchant.presentail"`. To activate Apple Pay in the native app: (a) In Apple Developer Portal → Identifiers → Merchant IDs, create `merchant.presentail`. (b) Enable the Apple Pay capability on the App ID `com.presentail.lb`. (c) In Stripe Dashboard → Settings → Payment methods → Apple Pay → App integrations, upload the Apple Pay certificate generated from that Merchant ID. A fresh EAS build is required after enabling the capability. If Apple Pay is not available at runtime on a test device, a `console.warn` is logged naming the merchant identifier and each required setup step — check device logs in Xcode or EAS build output.
- **Clerk middleware is gated on `CLERK_SECRET_KEY`**: `src/app.ts` only mounts `clerkMiddleware()` when the secret matches `^sk_(test|live)_`. Otherwise it installs a no-op shim that sets `req.auth = () => ({ userId: null, sessionClaims: null })` and logs one `WARN` at boot — Clerk sessions are then treated as signed-out and the legacy WP/social-JWT paths handle authentication. This is fail-closed (no auth bypass) and keeps fully public routes (`/api/woo/products`, `/api/homepage/*`, etc.) responding with 200 instead of 500-ing on every request when the key is missing or misformatted. Covered by `tests/clerkShim.test.ts`.
- **Apple Sign In web Return URL must be registered in Apple Developer Console**: The web `SignIn.tsx` sends `${window.location.origin}/sign-in` as the Apple Sign In `redirectURI`, which resolves to `https://presentail.com/sign-in` in production. This exact URL must be listed under **Apple Developer Console → Identifiers → Service IDs → `com.presentail.web1` → Sign In with Apple → Configure → Return URLs**. Without it Apple rejects the popup auth flow with `invalid_request` and the account picker never appears. Steps: (1) Log in at developer.apple.com → Certificates, Identifiers & Profiles → Identifiers → filter by "Services IDs" → click `com.presentail.web1`. (2) Check "Sign In with Apple" and click Configure. (3) Add `https://presentail.com` as a domain and `https://presentail.com/sign-in` as a Return URL. (4) Save and then click Continue / Save at the top level. If a staging domain (e.g. a Replit dev-preview URL) is also needed for QA, add it in the same dialog. `VITE_APPLE_SERVICE_ID` must equal the Service ID string (`com.presentail.web1`) set as a Replit secret for the button to appear in dev.
- **Clerk session token template must include email, name, and publicMetadata**: `resolveClerkSession` in `artifacts/api-server/src/lib/auth.ts` reads `email`, `first_name`, `last_name`, and `public_metadata` from the JWT session claims first, avoiding a round-trip to the Clerk API on every authenticated request. If any of those fields are absent (because the token template is not configured), the server falls back to `clerk.users.getUser()` and emits a WARN-level log (`auth.clerk: session claims missing email/name`). In the Clerk Dashboard → Configure → Sessions → "Customize session token", add the following to the JSON template: `{"email": "{{user.primary_email_address}}", "first_name": "{{user.first_name}}", "last_name": "{{user.last_name}}", "public_metadata": "{{user.public_metadata}}"}`. This must be done for both the development and production Clerk instances.
